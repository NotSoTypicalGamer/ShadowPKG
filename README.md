# ShadowPKG

Browse your `.pkg` library from any device and send packages to a jailbroken PS5 over your network.

ShadowPKG lists the packages in the folders you map, hands the console a link it will accept, and serves the file itself with resumable range requests. Packages that sit inside a stored `.rar` are served straight out of the archive, without extracting anything.

It is two files — `server.js` and `index.html` — on the Node standard library, with one deliberate exception: `basic-ftp` (`package.json`/`package-lock.json` at the repo root), used only by [FTP-connected consoles](#ftp-connected-consoles). Nothing else gets a new dependency because of it — no build step, and the included `Dockerfile` does the one `npm install` for you.

## What you need

- A **jailbroken PS5** running a DPI v2 payload: **Elf Arsenal** or **etaHEN**. ShadowPKG talks to whichever is running, and can send it a payload you pick ([Sending a payload](#sending-a-payload)); it does not fetch or choose one for you. A **jailbroken PS4** is supported in a limited, work-in-progress way, running flatz's [Remote Package Installer](https://github.com/flatz/ps4_remote_pkg_installer), which has to be open on the PS4 while you send. See [Sending to a PS4](#sending-to-a-ps4).
- Somewhere to run it: **Docker** (the included image), or **Node 18+** directly.
- The console and the server on the **same network**, since the console downloads packages from the server.

## What it does

- **Browse and search** one or more libraries, sorted by name, date or size. Search matches folder names as well as packages, and takes simple operators (`kind:`, `tag:`, `size:`, `title:`, `id:`) alongside free text.
- **Reads each package's own title** — along with its content ID, version and whether it's a game, an update or DLC, out of the package itself rather than guessed from the file name. Search covers the title, title ID and content ID as well as the path.
- **Gathers a game with its updates and DLC** under one row, newest update marked and duplicates counted, so three copies of the same release are obvious rather than scattered down the list.
- **Renames a package**, or a whole selection at once, offering a name built from what each package says it is.
- **Deletes a package**, behind a dialog that lists what's about to go and says plainly that it can't be undone.
- **Keeps a history** of finished downloads, sends, extractions and builds after the live panel forgets them, with a button to open where each one landed.
- **Says what's wrong up front** — a read-only library, a console that isn't answering, an address your console could never reach. A setup panel lists every check, and opens by itself the first time you load the page. It can also put the checks and the end of the log into one text to copy when you ask for help, with IP addresses and file names hidden.
- **Keeps its log on disk**, so the lines from before a restart are still there.
- **Stops cleanly.** A stop writes out everything the app was still holding, and a half-done unpack that a stop or a crash left behind is reported in the setup panel, with a button to remove it — never removed on its own.
- **Send to a console** — pick packages, pick where they go, send. Several consoles can be saved and switched between, and a send can target more than one at once. Sends to the *same* console queue behind each other and wait for the real download to finish, not just get accepted, before the next one starts (on a PS4, until the download has clearly begun; on any console, a download that makes no progress for 90 seconds stops holding the line) — sends to *different* consoles run independently, at the same time. A send is handed to the server in one request and worked through there, so shutting the tab or locking the phone loses nothing; see [Sending a batch](#sending-a-batch).
- **Needs attention** and **Homebrew** filters — surface packages worth a second look across a whole library (still unconfirmed, or a title nothing could name) and packages that look like scene tools rather than retail releases (a title ID outside Sony's own prefix for the platform), without hand-sorting the list. A package that will never get a title (an encrypted param.sfo, no PROSPEROPatches match) can be **Ignore**d from Needs attention so it doesn't sit flagged forever — per browser, like the theme, and reversible from the same button.
- **Recently added** — every package, archive and other file in the library, every folder at once, sorted newest first, for seeing what an extraction or a finished build added lately without opening each folder by hand.
- **Duplicates** lists the titles you hold more than once and suggests what to delete ([Duplicates](#duplicates)).
- **Game dumps** — a game kept as loose files, or still sitting inside a `.rar`, is recognised and checked ahead of time, and **Build .pkg** (or **Build from inside this archive**) hands it to a separate builder; if the archive lives on a slow share, `SCRATCH_LIBRARY` can stage the dump on a fast local disk first so the build isn't crawling the network the whole time ([Game dumps](#game-dumps)).
- **DLC for another region** — a DLC unlocker for a game's other release (a European DLC for the US game, say) is rebuilt by the container builder under that release's ids, with its own license entries, and lands in a folder of your choosing, by default `region change output` beside the DLC ([DLC for another region](#dlc-for-another-region)).
- **Install from a URL** — a fold under the list sends any `http://` or `https://` link to the selected console. Nothing is checked first, and the link need not point at ShadowPKG.
- **Cover art**, shown next to each row when you tick **Covers**. It is one image request per package, so it is off until you turn it on, and that is remembered per device.
- **Speaks three installers** — Elf Arsenal DPI v2 and etaHEN DPIv2 on the PS5, and Remote Package Installer on the PS4. The flavour is detected from the console itself, so swapping payloads needs no configuration.
- **Serves the file** with HTTP range support, so a console can resume and can fetch several chunks at once.
- **Live progress** — percent, speed and ETA per transfer, extraction and build, with stalled transfers called out and a stuck retry loop told apart from a merely slow one. A line too long for the bar scrolls by itself; touch it and drag sideways to read it by hand (it waits while you hold it and carries on a few seconds after you let go).
- **Activity** — the clock button at the top, or the bar under the header while something is going on, opens it: transfers, sends, extractions and builds in one list, with **Cancel**, **Clear** (for what has finished or given up) and **History**, and a first line saying whether it is safe to restart ShadowPKG right now. **Stop** on a transfer makes ShadowPKG refuse the console's next requests for that file, since a console cannot be told to cancel.
- **Copy link** — get the download URL for whatever you've selected, to paste into a console's own page or a download manager.
- **Reads packages inside `.rar`**, single archives and multi-part sets alike, without extracting them.
- **Unpacks the ones it can't read**, in place, with a progress bar. Extractions appear in the Activity dialog, so leaving the page doesn't lose sight of them, and a finished one offers to send what it produced or open the folder it landed in.
- **Shows how full a library is** ("412 GB free of 4 TB") in the Setup panel and, with more than one library, in the library menu, warns quietly when it runs low, and refuses an extraction that can't fit before it starts.
- **Deletes an archive once its packages are out**, listing every volume and anything else inside first, and can ask when an extraction finishes.
- **Console health check** — asks a console to install a link that points at nothing, and reports whether its installer actually tried to download it. That separates "the console's payload is broken" from "the file is bad", which is otherwise very hard to tell apart.
- **Themes** — fifteen built-in looks, from plain dark and light ones to console-inspired pixel-art ones with their own chunky borders and bevels, and your own: give it four colours in the theme maker, or drop a theme file or folder on the page. A theme can set density (`--pad`, `--row-h`, `--gap`), a raster page background, subtle animations (`@keyframes`, namespaced so they can never clash with the app's own) and a small blur; a **Background** section in the Themes menu sets a per-device page background image (cover, contain, fill or tile) independent of the theme. A theme installed on the server shows on every device, and the server can choose which one devices use until they pick their own. Text stays readable whatever colours you pick, and a theme that misbehaves can be switched off by opening the page with `?safe=1` ([Themes](#themes)).
- **Other files and Info** — files that are not packages are listed too, with a checkbox on every row, folders included. Select any file or folder and **Info** shows its type, location, exact size, dates, what is using it, what a folder contains, and an on-demand SHA-256. Text files open in a viewer and, up to 2 MiB, can be edited and saved in place ([Other files and Info](#other-files-and-info)).
- **FTP-connected consoles** — a jailbroken console's own FTP server (goldhen/etaHEN) can be browsed, uploaded to and downloaded from the same way a local library is, alongside DPI sending ([FTP-connected consoles](#ftp-connected-consoles)).
- **Move and copy**, between any combination of local libraries and FTP consoles, verified by size (or checksum) before a move ever touches the source ([Moving and copying](#moving-and-copying)).
- **Send a payload** — keep `.elf`, `.bin`, `.js`, `.lua` and `.jar` payloads inside SPKG, or pick one from a library or straight from your computer, and put it on a console at its own IP and loader port, from a button on the console's row ([Sending a payload](#sending-a-payload)).
- **ps5-tailscale** — on a PS5 with FTP set up, ShadowPKG reads its Tailscale config over FTP and, once [ps5-tailscale](https://github.com/holdmysocks/ps5-tailscale) has been run, puts a **Tailscale** button on the console's row (opens the status page) with the tailnet name, and a one-click **Re-send tailscale** to start it again after a restart.

## Install

### Docker

```bash
git clone https://github.com/NotSoTypicalGamer/ShadowPKG.git
cd ShadowPKG
docker build -t shadowpkg:latest .
docker run -d --name ShadowPKG \
  --restart unless-stopped --init \
  -p 12867:12801 \
  -v /path/to/games:/games \
  -v /path/to/appdata/ShadowPKG:/config \
  -v /path/to/downloads:/extra-libraries/Downloads \
  -e PUBLIC_BASE=http://192.168.1.10:12867 \
  -e ROOT_LABEL=Games \
  shadowpkg:latest
```

The `/extra-libraries` mount is optional: any folder mapped under it becomes a second library, named after the folder — `Downloads` above.

`--restart unless-stopped` brings it back after a crash or a reboot of the machine. `--init` puts a tiny init process in front of it, so a stop signal reaches the app and no finished unpacker is left behind as a zombie. See [Stopping, restarting and the health check](#stopping-restarting-and-the-health-check).

### Unraid

Build the image as above, then add the container from `shadowpkg.xml` (copy it to `/boot/config/plugins/dockerMan/templates-user/my-ShadowPKG.xml`, or fill the same fields in by hand).

After changing the code, remember that **rebuilding the image doesn't change a running container** — it keeps the image it was created with. Recreate it (Edit → Apply) to pick up a new build.

On Unraid, turn **Autostart** on so it comes up with the array. Autostart does not bring a container back after it exits on its own, so to have it restarted after a crash add `--restart=unless-stopped` to Extra Parameters, next to the `--init` the templates already put there.

### A second instance, alongside the first

Useful for trying a build without putting your working one at risk. `shadowpkg-exp.xml` is the same template set up to sit beside a stable install, with the four things that have to differ already different:

| | Stable | Alongside |
|---|---|---|
| Image tag | `shadowpkg:latest` | `shadowpkg_exp:latest` |
| Container name | `ShadowPKG` | `ShadowPKG_exp` |
| Port | 12867 | 12801 |
| `/config` | `…/appdata/ShadowPKG` | `…/appdata/ShadowPKG_exp` |

```bash
docker build -t shadowpkg_exp:latest .
```

The **image tag** matters most: build both from the same tag and whichever you rebuilt last is what *both* containers pick up when recreated. The **config folder** matters nearly as much — two versions sharing one `archives.json` and `packages.json` will overwrite each other's caches.

Build it from a checkout of the version you want to try: the command builds whatever is in the current folder. With plain `docker run`, change the same four things: `--name ShadowPKG_exp`, `-p 12801:12801` (the app still listens on 12801 inside; 12801 is only the port you reach it on), a different folder for `-v …:/config`, and the `shadowpkg_exp:latest` image. On Unraid, copy `shadowpkg-exp.xml` to `/boot/config/plugins/dockerMan/templates-user/my-ShadowPKG_exp.xml` the same way as the first.

Both can point at the same library; neither knows about the other. `APP_NAME` tells the two apart at a glance: the Unraid template already sets it to `ShadowPKG_exp`, and with plain Docker you set it yourself. Make sure the second one's `PUBLIC_BASE` carries its own port, or it hands the console links to the other one.

### Without Docker

Node 18 or newer. Run `npm install` once first — it installs the one dependency, `basic-ftp`, needed only for [FTP-connected consoles](#ftp-connected-consoles); the app won't start without it:

```bash
npm install
ROOT=/path/to/games CONFIG_DIR=./config node server.js
```

The config folder is made if it is not there. On Linux the Setup panel will still warn *Settings will be lost* unless that folder is a mount of its own, because the check is written for containers; the settings are saved all the same, and the warning can be hidden for a day. In PowerShell, set the variables first: `$env:ROOT='D:\Games'; $env:CONFIG_DIR='.\config'; node server.js`.

Extraction needs `unar` or `unrar` on the PATH (`bsdtar` and `7z` are tried as fallbacks, but read fewer archives); everything else works without it.

### First start

Open `http://SERVER-IP:12867`, by the server's LAN address rather than `localhost`, so that it matches what the console will be given (on Unraid, the container's WebUI link opens it). The Setup panel opens by itself the first time and lists anything to fix.

A fresh install already has one console, `PS5`, at `192.168.1.50:12800` (or whatever `PS5_HOST` says). That is only a placeholder and reads as not answering until you change it: click the console's name at the top right, press **Edit**, put your console's IP address in *IP address:port* (12800 is assumed if you leave the port off), **Save**, then **Test**. **Discover** and **Add a console** are in the same dialog. To send, open a folder, tick a package, and press **Send to** in the bar that appears at the bottom; see [Sending a batch](#sending-a-batch).

### Stopping, restarting and the health check

A stop — `docker stop`, an update, a reboot — is a `SIGTERM`, and Docker kills the container ten seconds later. ShadowPKG uses those seconds. It stops taking new connections, writes out whatever was still waiting for its delay (package details and the archive index wait 30 and 5 seconds; history and titles 5), along with the console list, settings, held sends, build jobs and the record of any unpack under way, logs `shutting down (SIGTERM)`, and exits, always within 8 seconds. Ctrl-C does the same when you run it by hand, and a second one exits at once.

- **A stray failed promise** is logged with its stack and the app carries on, rather than dying in the middle of a long send.
- **An error nothing expected** is logged, state is written out as far as it can be, and the process exits with code 1 — which is what `--restart` acts on.
- **An unpack under way is ended, not waited for.** Unpacking a big dump can take longer than any stop timeout is worth, so the extractor is stopped and its half-filled hidden folder stays where it is and is written down, and the Setup panel offers to remove it at the next start (see [Interrupted unpacks](#interrupted-unpacks)). It also means a longer `--stop-timeout` gains nothing here: the app is gone within 8 seconds either way, inside Docker's default ten.

`GET /healthz` answers `ok` straight from memory, with no disk, console or library behind it, so it says the process is up and turning over, not that your share is mounted (the Setup panel says that). The image's `HEALTHCHECK` asks it every 30 seconds and Docker marks the container `unhealthy` after three misses in a row. Docker does not restart it for that by itself. The builder image has no health check on purpose: a restart would kill a build in progress.

## Configuration

Everything is an environment variable; nothing needs editing in the source.

**Changing them without recreating the container.** The ones that can change while the app runs are also in **Setup → Settings**: extractions at once, the scratch library (a list of your libraries, not a typed id), the low-space warning, showing every file, the notification address, events and format, following a console that moved, and logging every range. Each row shows where its value comes from (*saved here*, *from the variable*, or *default*), saves the moment it is changed and takes effect at once, and a value that does not work says so (a scratch library that is not one of your libraries, for instance). A value saved there beats the variable, the same way the public address already does, and is kept in `settings.json` in the config folder; **Use the variable** hands it back. The notification address is never sent back to the page once saved: the row shows only its host, and the box is for pasting a new one or turning it off. Under *Fixed when the container is created* the rest are listed read-only with where each came from, so it is easy to see what the container is really running with. The password is left out of the window on purpose: a wrong change there can lock you out.

Only that one path is affected — a package extraction, "Extract all files", and a build started by hand on a dump already on real disk are untouched. Once the build finishes, the package is moved back to where the archive lives (verified by size first, the same as a person's own Move) and the scratch copy of the dump is removed. The library menu marks it with a **scratch** chip, since the setting is otherwise silent — nothing about the entry itself would say it's spoken for. ### State files

The state files (`profiles.json`, `settings.json`, `libraries.json`, `packages.json`, `archives.json`, `titles.json`, `history.json`, `held.json`, `builds.json`, `extracting.json`, `transfers.json`, and the `themes` folder that holds installed themes) are written off the main thread, in slices for the big ones, then renamed into place, so saving a large library's details does not make the page hang. The ones that wait a few seconds after their last change are also written when the app is told to stop.

## Archives

Repacked releases often wrap a single `.pkg` in a `.rar` with **no compression**, because a package is already compressed and won't shrink. ShadowPKG reads the archive index and maps the console's range requests onto the package's byte run inside it, so those releases need no extraction, no second copy and no waiting. RAR4 and RAR5 are both understood.

Multi-part sets work the same way, in both the `.part01.rar` and the older `.rar`/`.r00` styles: a package split across volumes is still one unbroken byte run, so its chunks are served in order without joining the files first.

With **Group** ticked (the default) a set is listed as **one row**, the first volume standing for all of them. Untick Group and the other volumes are listed too, each under that row with its part number and size (*part 2 of 13*); they are for looking at, not for acting on alone, since a volume moved or deleted by itself would split the set — the set's own row takes every volume with it. The row says how many there are (a **13 parts** chip), and its size is all the volumes together, not the first file's. **Move** and **Copy** of that row take every volume with it, one transfer each, queued together in Activity, so a set is never left split with its later volumes behind; **Delete archive** already removed every volume, and Rename is refused for the same reason.

Every `.rar` is listed with a chip saying where it stands:

| Chip | Meaning |
|---|---|
| `served from here` | Its package is listed above and streams straight out of it. |
| `already extracted` | The package is unpacked next to it; nothing to unpack. **Delete archive** removes what is left of it (below). |
| `compressed` | The package is really compressed. **Extract here** unpacks it in place. |
| `password protected` | Needs a password; unpack it yourself. |
| `split across volumes` | The package continues into a volume that isn't part of this set. |
| `incomplete set` | Volumes are missing, and it says how much of the package is present. |
| `no pkg inside` | A dump or some other archive with nothing a console can install. It stays labelled that way, but **Extract all files** unpacks every file, with its folders, into a new folder beside the archive (named after it; a name already taken gets `-2`, `-3`, …). It works in a hidden folder first and only renames it into place when the tool finishes cleanly, so a failed run leaves nothing half-unpacked. Like the rest, `.rar` only. |

Extraction runs in a hidden folder and only moves out files that match the size recorded in the archive index, so a failed run never leaves a half-written package behind. If one tool only manages part of an archive, the next is asked for the rest, and anything still packed is reported rather than passed off as success.

**Room, and names already taken.** Before an extraction starts, the free space next to the archive is checked against what its packages need (the hidden folder holds them all before the last step, and the final rename costs nothing). One that will not fit is refused up front, with the size it needs and the space that is free; a queued one is checked again when its turn comes, since the job ahead of it may have used the room up. That figure is what the share reports, so it can be more generous than the one disk a file lands on (on Unraid, `/mnt/user` is the pooled share), but when it says there is not enough, that is true.

Nothing is ever replaced. If a file already has a package's name at a different size (a hand-fixed or newer copy, or another package that shares the name), that package is left alone and reported as skipped — *a file of that name is already here at a different size; move or rename it first* — and the job ends as failed rather than done, saying which were skipped. When every package in the archive is in that position the request is refused at once, so gigabytes are not unpacked to be thrown away. A package a console is downloading right now is not swapped under it either.

**Delete archive.** "Extract here" leaves the archive beside what came out of it, so the library holds every repack twice. Once every package inside has a file of the same name and size next to it — the same test that gives a row its *already extracted* chip — that row gets a **Delete archive** button. A dump pulled out with [Build from inside this archive](#a-dump-inside-a-rar) is covered too: once its own folder verifies against the archive's listing (and any separate package inside is also accounted for), the archive can go the same way — it doesn't wait for the build itself to finish, only for the dump to be genuinely out, the same standard a package already gets held to. It opens a dialog that lists every volume of the set with its size and the total, and any file inside that is not a package (a readme, samples) and would be lost with it, and says plainly that this cannot be undone: the files are removed from disk, not moved anywhere. Nothing happens until **Delete archive** is pressed inside it; **Keep it**, Esc and a click outside all leave everything alone. It removes every volume of the set (`.part01.rar`, `.part02.rar`… or `.rar` with `.r00`, `.r01`…) and nothing else.

It is refused while an extraction of that archive is running or waiting, while a console is pulling a package straight out of it, on a library mounted read-only, when the archive is cut short or the set is visibly incomplete (a gap in the numbering, or a stored file that runs on into a volume that is not there), and whenever a package inside is not unpacked yet — the dialog says which. Like deleting a package, it leaves nothing in History. `.zip` and `.7z` are not offered: nothing can be read from inside them, so there is nothing to check.

**Asked after extracting.** When an extraction you were watching finishes and its archive is now a second copy, the page asks — *Delete the archive?* — with the same list, and two buttons: **Keep it** (the default) and **Delete archive**. Several extractions finishing together are asked about one at a time, never on top of another dialog. If the page was closed or the phone locked when the job finished it cannot ask then, so the finished extraction in **Activity** has a **Delete archive…** button for as long as the archive is still left over (the folder's row keeps its own button regardless). **Extract all files** does not ask: it unpacks a whole folder, which is not the same as the packages being out beside it.

That page-wide question is for packages unpacked with **Extract here**; a dump built from inside an archive has its own box on its row (see [A dump inside a `.rar`](#a-dump-inside-a-rar)) and asks at the end of the build instead. The question has a **Don't ask me after extractions** box. Ticking it stops the question on that browser (it is remembered there, as a per-browser choice like the theme) but leaves the row's button and the Activity button working. To turn it back on, tick **Ask whether to delete an archive after extracting it**, which sits under a folder's list whenever that folder has archives in it.

**`.zip` and `.7z`** files are listed too, with a `zip archive` / `7z archive` chip. Nothing is served straight to a console from inside them the way a stored `.rar` entry can be, but they get the same **Open** button as `.rar` (see below) and offer **Extract all files** (into a folder named after the archive, as above); the room next to them is checked first when 7-Zip can report the unpacked size. Multi-part `.7z.001` sets are not handled.

**Open.** Every archive row also gets an **Open** button — a listing of every entry inside it with its size, without unpacking the whole archive. `.rar` reads its own headers directly; `.zip` and `.7z` are listed through 7-Zip's own technical listing mode instead (whichever of `7zz`/`7z`/`7za`/`7zr` is installed — the one tool whose listing output is stable and machine-parseable enough to trust; a container with none of those installed gets a plain refusal rather than a guess at `bsdtar`'s or `unzip`'s own plain-text output). Eight or more entries gets a filter box above the list. Clicking an entry reads it: for one small enough and text-shaped, its contents (a stray `.nfo`, a readme, a small `.txt`) show right there, pulled out to a scratch spot and gone again the moment it's read; too big (over 1 MiB) or not text-shaped says so instead of showing anything. Ticking one or more entries' own checkboxes (or **Select all**, scoped to whatever the filter currently shows) and pressing **Extract selected** instead pulls out exactly those files for real, each landing at its own path inside the library the same way the archive's own folders are laid out — for pulling one or two things out of a big archive without unpacking everything. Selections are kept while you go back and forth between the listing and a file's contents, so picking several across a few clicks doesn't lose earlier ones. Extracting is refused for a name already sitting there at a different size, the same rule every other extraction mode already keeps, and it never offers to delete the archive afterward — a hand-picked few files is never "everything the archive needed to be unpacked."

**Several at once.** Two extractions run at the same time by default (`EXTRACT_PARALLEL`), each in its own hidden folder, so a big RAR that keeps one core busy no longer holds up the next one behind it. A queued extraction says whether it is waiting for a free slot or for room on the disk, and starts by itself when either clears.

**Cancel.** Every extraction in the Activity dialog has a **Cancel** button. A queued one is just dropped; a running one has its tool stopped and its hidden folder removed, so nothing half-unpacked is left. A package-only extraction keeps any packages that had already come out whole.

It needs an extractor in the container and the library mounted read/write. The included `Dockerfile` installs **unar**, which is the one that reads multi-volume RAR sets — bsdtar handles a single `.rar` but not a set, and both Alpine 7-Zip and Debian p7zip ship without the RAR codec entirely. It also installs **unrar** (RARLAB's own extractor, tried first when present) for the RAR5 compression variants none of the above can decompress at all; it's free to use but not open-source, so the image enables Debian's `non-free` component to get it — the one non-free package in an otherwise dependency-free build.

### Interrupted unpacks

Both kinds of extraction unpack into a hidden `.shadowpkg-extract-<id>` folder beside the archive and remove it when the job ends. If the container is stopped, runs out of memory or crashes partway through a 60–140 GB unpack, that folder is left behind holding tens of GB, and it is dot-named, so no list shows it unless **Hidden** is ticked. ShadowPKG writes each unpack folder into `extracting.json` in the config folder before it makes it. At the next start, any folder written down that is still on disk is reported: the Setup panel gets a quiet warning, counted on the icon and hideable for a day like the others, saying **Leftover unpack folders: N (X GB) from an interrupted extraction**, with **Review and remove…**. That opens a list with the library, the folder, the archive it was unpacking and its size, and **Remove** for each one or **Remove all**.

**Nothing is ever removed by itself.** Removing one deletes its contents from disk for good; the archive it came from is untouched. The request is refused for anything that is not a folder ShadowPKG wrote down, is not named exactly like an unpack folder, or is not inside a library. A folder whose path has gone missing (a share not mounted just now) stays on record until a month after its unpack began, and is forgotten after that. Sizes are worked out in the background and capped for a very large tree (shown as "at least"). This needs the config folder to be writable, as everything else that is remembered does.

## Duplicates

The **Duplicates** pill beside the filters (Needs attention, Homebrew) lists titles that are in the library more than once, using what each package says about itself (so only packages already read are compared; open it again if the note says the library is still being read). Two kinds show up together, each with its copies labelled:

- the same version twice (`likely copy`), and
- older versions of a title you also have newer (`older`).

They are *likely* copies because they are matched on content ID, version, a size within about 1 percent and the numbers in the file name, never on the bytes: nothing is hashed, so a match is still not proof of identical files, and a hand-fixed copy only a few KB off is still called a likely copy.

One copy is marked `keep`: the newest version, and among equals a real file over one inside an archive, then the first library, then the shortest path. Everything else that is an ordinary file is suggested for deletion, and **Review N suggested deletions** (the button carries the count) opens the normal delete dialog with those ticked. Nothing is deleted until you confirm there, and a package inside an archive is never offered, because it is part of that archive. Your own tray selection is put back afterwards.

**Names matter too.** Several different packages can share one content ID (the themes of a collection, `Theme_1` and `Theme_2`), and then the content ID and version say nothing about which are copies. So files under one content ID are only compared with each other when their names carry the same numbers (ignoring a version, an ID, a trailing `(2)` or `- Copy`): `Theme_1.pkg` in three folders is a package present three times, `Theme_2.pkg` is another, and each is its own entry, headed with the file name, instead of one entry calling the lot extra copies of the first. Names that differ in a number only count as different packages when they share a version: at different versions the number is usually the version itself (`Game v1`, `Game v2`), so those stay together as older and newer.

**Where it can't be sure, it ticks nothing.** A release can give a base game and its update the same content ID and even the same version (see [One game and everything that belongs to it](#one-game-and-everything-that-belongs-to-it)), so a group that holds a game beside an update, at the same version or not, is shown with a `game and update, check` chip. A group whose newest copies differ in size by more than about 1 percent, or where an older file is more than twice the size of the newest (a base beside its update, when the update reads as a game, as a PS5 one may), gets `sizes differ, check`. Any group where a package does not say what kind it is, has no version, or only has a content ID because of its file name gets `not sure, check`. None of them has a keep or a suggestion: you look at it and decide.

**All libraries.** With more than one library mapped, a switch at the top of the dialog compares them all with each other, not just the one you are in. Every row then says which library it is in (as does every row of the delete dialog), and where nothing else decides it the copy in the first library is the one kept. A file that two libraries both list, because their folders overlap, is one file and never a pair of copies.

## Game dumps

A dump is a game as loose files — a folder with `sce_sys/param.json` and no package. A console can't install one, but it can be repacked into a `.pkg` with a separate tool. ShadowPKG doesn't ship or run any such tool; what it does is recognise a dump, say what it is, and check it ahead of time.

A folder that is a dump gets a **dump** chip in the listing, showing the title and version from its `param.json`. Open it and a card at the top offers **Check this dump**, which walks the whole tree — it can take a while over a network share, so it runs on request rather than on every view — and reports. Before a first check, a second button, **Check & Build**, does the same check and, if nothing blocks it, starts the build right away with the default options — the same two steps as pressing Check this dump and then Build .pkg, without waiting on the first one to look at the result yourself first.

- the content ID, the 96-byte `sce_sys/keystone`, `applicationCategoryType`, and `kernel.addcontMountLevel`;
- whether the presentation images (`icon0`, `pic0`, `pic1`, `pic2`) are the colour mode a repack needs, and whether any would be rebuilt from a `.dds`;
- symbolic links, a loose `.pkg` file with no folder of its own, and hidden folders inside the dump, all of which a repack trips on or quietly packs into the game. A folder that directly holds a `.pkg` is treated differently: most commonly a DLC or unlocker shipped alongside the main game's loose files, so that whole folder is left alone entirely — not walked, not counted, not packed into the game — rather than blocking the build;
- the file count, the total size, the package size it would come out at, and the free space where the result would be written.

Nothing in a dump is ever changed. The check is read-only.

### A dump inside a `.rar`

Scene "PS5 Dump" releases usually ship the dump compressed inside a `.rar` rather than as loose files, so ShadowPKG also looks for a dump-shaped folder (one holding `sce_sys/param.json`) inside every `.rar`'s own listing — cheap and read-only, nothing is extracted just to check. An archive holding one gets a **dump inside** chip and a **Build from inside this archive** button (a picker if it finds more than one), alongside whatever the archive's usual chip already says about any `.pkg` in it. A line under the button spells out exactly what pressing it will do — where the dump lands, whether it'll be sent anywhere, whether it comes back here afterward — since the whole chain runs with no further clicks once started.

Pressing it pulls out only that dump's own folder — not the rest of the archive — into a hidden folder first, renamed into place once it is complete, the same as any other extraction. Refused up front if a folder of that name already sits where it would land (beside the archive, or on `SCRATCH_LIBRARY` if that's set) — the archive itself stays fully live and buildable after a first extraction, so nothing stops a second click from quietly doubling the disk cost of a dump that can run past 100 GB unless this says so first; open the existing folder to see whether it's already the dump you're after, or move/rename it, before trying again. The moment it lands, ShadowPKG runs it straight through the same read-only check "Check this dump" does and, if that passes, starts a build automatically with default options — no separate click. A dump that turns out not to be valid, or that fails the check, is left exactly where it landed with nothing deleted and no build started, and the job says why — including running out of room: the automatic build refuses to start rather than run for hours toward a package it won't have space to finish, where a person clicking **Build .pkg** by hand would only get a warning they can choose to run past. Scoped to `.rar` for now (`.zip`/`.7z` dumps aren't offered); a dump inside a set that can't be read whole (a missing or cut-short volume) isn't offered either. Once the dump is out and verified, the archive itself becomes eligible for [Delete archive](#archives) the same way a fully-unpacked package archive already is. A **Ask me whether to delete this archive when it is done** box on the archive's row (ticked to begin with) makes that a question at the end of the whole chain: when the build has finished and, with `SCRATCH_LIBRARY`, its package is back beside the archive, the usual dialog lists every volume and everything else inside and asks — *Keep it* is the default, nothing is deleted without pressing **Delete archive**. The dump is checked against the archive's own listing (name and size of every file) at the moment it comes out; with `SCRATCH_LIBRARY` that is remembered (in `dumpbuilds.json` in the config folder) since the dump itself is removed from scratch once the package is back, and it only counts while the built package is still beside the archive. A build that fails, or a dump that did not pass its check, is never asked about: the archive is still what it came from.

**Building from fast storage instead of a slow share (`SCRATCH_LIBRARY`).** If the archive lives on a slow share — a NAS over the network, a spun-down array disk — point `SCRATCH_LIBRARY` at a fast local disk mapped as one of your libraries (see [Configuration](#configuration)) and the dump lands there instead of beside the archive: the build then reads it from fast local storage instead of crawling the share for the whole build, which is where most of the wall-clock time on a big dump goes. Once the build finishes, the package moves itself back to sit beside the archive (verified by size, same as a person's own Move) and the scratch copy of the dump is cleaned up; a build that's still running, or one that failed, leaves the dump on scratch untouched rather than risk losing the only copy. This is one half of the picture — a builder reading a dump over a share has always coped by copying it locally first ([`dumpCache`](#building-on-the-server-instead-wine-in-a-container)); pointing `SCRATCH_LIBRARY` at the same disk a container builder already uses as its own scratch avoids that builder-side copy happening a second time, but confirming that alignment is a matter of how the two are mounted, not something this app can see from here.

**Send to a console when it finishes.** Right beside the button, when a console is selected, a **Send to *console*  when it finishes** checkbox offers the same choice the real-disk dump's own "Build .pkg" panel already has (one shared setting between the two). Ticked, the finished package is sent the moment the build ends — straight from wherever it actually landed, `SCRATCH_LIBRARY` or not, so a console pulling it off a fast disk downloads faster too — and the package only moves back to sit beside the archive, and the scratch copy gets cleaned up, once the console has finished pulling it (or has stopped asking): a send counts as "handed off" the moment the console accepts it, well before a large package has finished downloading, so the move waits for the download itself rather than starting with the acceptance. The one case this doesn't cover: a **held** send (a PS4 whose installer isn't open) leaves the scratch copy in place, uncleaned, until the installer opens and the hand-over actually happens — a real gap, not a deliberate choice, and one more instance of [PS4 sending](#sending-to-a-ps4) already being limited/work-in-progress.

### Building a package from a dump

Once a dump passes its check, **Build .pkg** prepares a job. ShadowPKG itself never runs a repack tool and ships none; the job is a hidden folder beside the dump (`.shadowpkg-build/<id>/`, listed only if **Hidden** is ticked) that a builder picks up, using a repack kit that you supply: either a script on a Windows PC, described next, or the builder container on your server ([below](#building-on-the-server-instead-wine-in-a-container)), which is the one for Unraid. Quick validate, the options, patches and Cancel build are under [Options, patches, cancelling and the builder's log](#options-patches-cancelling-and-the-builders-log).

**Several dumps at once.** Tick more than one dump folder in a listing and the selection tray gets a **Build** button. One already checked and passed starts building right away; one not yet checked gets its check started instead (build it again, by hand or by re-selecting it, once that check passes) — the same two steps a person clicking "Check this dump" then "Build .pkg" on each folder individually would take, just fired for the whole selection in one click rather than one folder at a time.

**Queue order.** A builder is one job at a time, so several waiting builds sit in line; a waiting card and its Activity row both say where ("2 of 3 waiting"), and while it's still waiting **Move up**/**Move down** buttons move it earlier or later — a real change to which one gets picked up next, not just to the list on screen. A build already running can't be reordered, only cancelled.

On the PC, copy `tools/windows` somewhere, copy `builder.example.json` to `builder.json` and fill in where the kit, Python 3.9+ and scratch space (`temp`) live, ShadowPKG's address (`server`, e.g. `http://192.168.1.10:12867`) and, under `libraries`, where this PC sees each library, keyed by the library's id (its name in lower case: `games` for the main library, `seed` for one called Seed) — and, if ShadowPKG has an `ACCESS_PASSWORD`, the `user` and `password`; keep that file private, then approve the kit once:

```
powershell -ExecutionPolicy Bypass -File ShadowPKG-Build.ps1 -Trust
```

That lists every program and script in the kit with its hash and asks you to type `YES`. From then on the builder refuses to run unless every one of those files is exactly as approved — nothing added, removed or changed. Some kits contain modified, unsigned or online-capable programs, so it also prints a `New-NetFirewallRule` command for each program in the kit; paste them once into an elevated PowerShell (Run as administrator) to stop those programs reaching the network. Keep the kit out of any synced folder such as OneDrive.

Then run `powershell -ExecutionPolicy Bypass -File .\Install-ShadowPKG-Builder.ps1` once. It registers a scheduled task that starts at every logon and runs `ShadowPKG-Watch.ps1` hidden, so there is nothing to open: every 30 seconds it asks ShadowPKG whether a build is waiting, and runs it if so. (A task rather than a Windows service, because a service runs outside your session, where mapped drive letters like `R:` don't exist. `-Uninstall` removes it; its log is `watch.log`.) You can still run `ShadowPKG-Build.ps1` by hand, and `ShadowPKG-Build.cmd` does the same with a double-click.

Either way, the builder asks ShadowPKG for the waiting job, reads the dump straight from the library share, builds, and moves the finished `.pkg` next to the dump; the card shows progress meanwhile, and the PC is kept awake while a build runs. A job that cannot start says why on its card rather than sitting on "waiting". With `staging` set to a folder on the PC, the build happens there and the library only ever receives a complete file, copied under a name that isn't a package and renamed into place last. If the library is on a network share, also add `"dumpCache": "C:\\ShadowPKG-Build\\dump"` (a fast local folder) to `builder.json`: the packer memory-maps the dump, which crawls over a share, so the dump is copied there first and removed after a successful build (`"keepDumpCopy": true` keeps it).

A build also gets its own bar under the downloads bar, visible from any folder. A finished, failed or cancelled build keeps that bar until you clear it in **Activity** (**Clear** on its row, or **Clear** at the top); with no build to show the bar is gone, and the downloads bar above it is not affected either way. The **Activity** dialog has a row per build with its phase, progress, size and speed and, where they apply, **Send**, **Open folder**, **Go to game**, **Cancel build** and **Clear**, and keeps a finished build for a day.

A finished job is added to the history, and **Clear** removes its folder. `-DryRun` does every check and runs nothing.

#### Building on the server instead (Wine, in a container)

`tools/container` builds the same jobs on the server itself, running the kit under Wine in a container, so no PC has to be involved, the dump is read from the server's own disks, and the kit can be given no network at all. It speaks the same job protocol as the Windows builder, so ShadowPKG needs nothing extra, and it finds jobs by reading ShadowPKG's `builds.json` from a read-only mount rather than over the network. It has built a 140 GB game from start to finish (packing took about 40 minutes on a many-core server). Treat it as experimental: it depends on Wine running a Windows program that was never meant for it, and whether the finished package installs on a console depends on the kit, not on this.

What it needs: a Docker host, the kit **extracted** into a folder (`build-from-folder.ps1`, `scripts/` and `toolchain/` directly inside it), about 2 GB for the Wine environment, and a work folder with room for a copy of the kit plus the package being built. Nothing of the kit is in the image; it is mounted read-only.

**Room, checked before it starts.** A job refuses up front rather than run for hours (kit copy, dump copy, packing) only to fail once the work disk actually fills: the kit's own size, the dump's size when `COPY_DUMP` copies it there first, and the package size "Check this dump" already estimated, checked against the work folder's free space. The dump and estimate come from `job.json` — ShadowPKG measured them during the check, so this never re-walks a dump that can run past 100 GB just to ask how big it is. A job.json without either figure (from before this, or a check that never measured them) is not blocked over a guess — only a build this can actually confirm doesn't fit is refused.

**A genuinely stuck build stops itself.** "Nothing heard from the builder for a few minutes" already showed on a build that had gone quiet; now, if that stretches to 30 minutes straight with no heartbeat (Wine crashed or hung — the builder writes progress every 15 seconds regardless of how fast the packer itself is moving, so real silence this long is never just a slow phase), ShadowPKG asks it to stop the same way pressing Cancel would. The card and Activity say it was stopped automatically and why, rather than reading as if someone chose to cancel it. A build that's still genuinely working, however slowly, is never touched.

**Dump folder names.** A folder read in place has to keep the characters a Windows path (and so Wine, which the kit runs under) can have — no `< > : " | ? * \` or control characters — so a release named with a colon or similar (`Game: Subtitle`) is refused, with the check saying so up front rather than failing only once a build is actually attempted. The job's own bookkeeping (its hidden `.shadowpkg-build/<id>/` folder, and the folder the finished package lands in) never reaches Wine, so those are read and written with whatever a real filesystem allows — only the dump itself, and a patch's reference package, keep the stricter rule.

##### The easy way: a guided installer

Pick the one for where Docker runs. Both do the same three things, and both need this repository's `tools/container` folder on that machine (download the repository, or clone it):

1. build the image;
2. run the **one-time setup** in a throwaway container that **is** allowed to use the network (Wine, .NET, the VC++ runtime and Python are downloaded, 10 to 20 minutes; then the kit is tested and its files are listed, and you type `YES` if you accept them);
3. start the real container with the network **off**.

**Unraid, a NAS, or any Linux Docker host.** In a terminal (Unraid: the terminal button in the web UI), from `tools/container`:

```
sh install.sh
```

It asks for five folders: the extracted kit, your game library (the same one ShadowPKG uses), ShadowPKG's own config folder (where its `builds.json` lives), a folder for the builder's own settings and logs, and a fast scratch folder with room for a copy of the biggest game. Folder names must not contain spaces. The defaults are Unraid paths; type your own if yours differ.

**Windows with Docker Desktop.** Start Docker Desktop, then in PowerShell, from `tools\container`:

```
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

It asks for four folders (the extracted kit, the library, ShadowPKG's config folder, and a folder for the builder's own logs; spaces are fine). Windows differs from a NAS in two ways the script already handles: Wine cannot run from a Windows folder, so its environment and the scratch space live in Docker volumes (Docker Desktop's disk image needs room for the biggest game plus its package, see Settings, Resources), and reading a dump through Docker Desktop's file sharing is slow, so the dump is copied into the scratch volume first (`COPY_DUMP=1`). The ShadowPKG config folder has to be the one ShadowPKG really uses; if ShadowPKG runs in Docker Desktop too, that is the folder mapped to its `/config`. If you would rather not run Docker on the PC at all, the PowerShell builder above (`tools/windows`) runs the kit directly.

**Both installers** save your answers, so later you can update with nothing to type: `sh install.sh --update` on Linux, `powershell -ExecutionPolicy Bypass -File .\install.ps1 -Update` on Windows. That rebuilds the image and recreates the container, and it refuses while a build is running (`--force` / `-Force` overrides, and the build is lost). `--dry-run` / `-DryRun` prints the docker commands without running any, and `--yes` / `-Yes` takes the saved answers or defaults without asking. If setup fails partway, fix what it says and run the installer again; it picks up where it stopped. If your kit ever changes, run it again too: the container refuses to use a kit that no longer matches what you approved.

The steps below are what the installers do, for doing it by hand or for Unraid's template.

Once the builder has been seen, the builder's status is in the **Setup and network** panel (ready, needs setup, or not running). A problem with it is counted on the setup icon, and the panel lists every check: kit found, Wine/Python/.NET set up, kit starts under Wine, kit approved and unchanged, work folder writable with room, library writable, and whether the container can still reach the internet (worth fixing once setup is done). `docker exec -it ShadowPKG-Builder node /app/runner.js status` prints the same list from a terminal, and `... runner.js setup` runs the three setup steps in order, skipping what is already done.

1. **Build the image** from this repository's `tools/container` folder:
   ```
   docker build -t shadowpkg-builder tools/container
   ```
2. **Create the container.** On Unraid, copy `shadowpkg-builder.xml` to `/boot/config/plugins/dockerMan/templates-user/my-ShadowPKG-Builder.xml` and add it from the Docker tab. Before you apply it, set **ShadowPKG config (read-only)** to the folder mapped to ShadowPKG's own `/config` (`/mnt/user/appdata/ShadowPKG` for the standard install; the folder of the second instance if that is the one it should build for): a builder pointed at the wrong one never sees a job. **Kit**, **Library** and **Work folder** have no default. Anywhere else:
   ```
   docker run -d --name ShadowPKG-Builder \
     -v /path/to/kit:/kit:ro \
     -v /path/to/library:/games \
     -v /path/to/shadowpkg-config:/spkg:ro \
     -v /path/to/builder-config:/config \
     -v /path/to/builder-config/prefix:/prefix \
     -v /path/to/fast-disk:/work \
     shadowpkg-builder
   ```
   `/games` must be the same folder ShadowPKG's own library points at, so job paths line up. **Every other library is found by itself:** ShadowPKG writes the list of its libraries and their folders (`libraries.json`) into its config folder, and the builder uses each one that exists at the same path inside its own container. So to build in another library (say `/extra-libraries/Seed` in ShadowPKG), add one **Path** to the builder container with that same container path pointing at the same host folder, read/write, and apply. The guided installers mount only the main library, at `/games`, and `--update` recreates the container from its saved answers, so a Path added to a container they made is lost on the next update; for a second library, create the container from the template or the `docker run` above. Nothing else needs setting; the builder's startup check says `MISSING library "Seed" is in ShadowPKG at /extra-libraries/Seed but is not mounted here: add a Path ...` for any it cannot see, and ShadowPKG's build card says the same when a builder is running but cannot see the library. `LIBRARIES` (`id=path`, comma separated, e.g. `seed=/seed`; the id is the library's name in lower case with anything but letters and digits made a dash, so `Seed` is `seed` and the main library is `games` unless you changed `ROOT_LABEL`) is only for a folder mounted at a *different* path than in ShadowPKG, or with a ShadowPKG old enough not to publish its list; where no list is published, setting it replaces the default `games=/games`, so list that too. `/spkg` is ShadowPKG's **config** folder (where `builds.json` lives).
3. **Set it up, once, with network on.** The short version is `docker exec -it ShadowPKG-Builder node /app/runner.js setup`, which does the three steps below in order. Setup downloads .NET, the VC++ runtime and Windows Python into the Wine environment, and takes a while; separately, you can run it detached and follow the log:
   ```
   docker exec -d ShadowPKG-Builder node /app/runner.js init
   tail -f /path/to/builder-config/init.log      # wait for "INIT COMPLETE" (or "INIT FINISHED WITH PROBLEMS" / "INIT STOPPED" if it failed)
   docker exec -it ShadowPKG-Builder node /app/runner.js smoke
   docker exec -it ShadowPKG-Builder node /app/runner.js trust
   ```
   `smoke` runs a real Python statement and the kit's packer with `--help`, and says which layer failed if either does. `trust` lists every program and script in the kit with its hash and asks you to type `YES`; from then on the runner works on a private copy of the kit and refuses to run unless it matches exactly.
4. **Recreate the container with network None.** Nothing after setup needs it. On Unraid, set Network Type to None and apply. Anywhere else, `docker rm -f ShadowPKG-Builder` and run the `docker run` from step 2 again with `--network none` added, and `--restart unless-stopped`, or the builder stays stopped after a reboot of the host. It then polls for jobs on its own, so pressing **Build .pkg** in ShadowPKG is all that is needed.

Things worth knowing:

- **A restart kills a running build.** Packing cannot resume. Anything that stops containers on a schedule — a backup plugin such as Unraid's Appdata Backup, an auto-update job, a "restart all" — will destroy it, so exclude this container from those. A runner that starts up marks a job it left running as failed, with the reason, if that job has been quiet for more than two minutes; after a faster restart the job still reads as running, then as stalled after three minutes, and you clear it and build again.
- **Rebuilding the image does not change a container that already exists.** Recreate the container to pick up new code.
- **One runner per ShadowPKG.** Run this or the Windows builder, not both; a job is claimed by whichever writes its `state.json` first. Until the kit has been approved, the runner leaves waiting jobs alone.
- **Slow reads.** The packer memory-maps the dump's files. If the library is on a slow or network filesystem, set `COPY_DUMP=1` to copy the dump to the work folder first: the template's `COPY_DUMP` variable, `COPY_DUMP=1 sh install.sh --update` (the installer saves it; `install.ps1` always sets it), or `-e COPY_DUMP=1` by hand. The work folder then holds the copy and the package, so give it room for both.
- **The library is mounted read/write**, because the finished package and the progress files are written there. Modified or unsigned kit programs running in a container with no network can still touch files in that one folder; that is the limit of the containment.
- **Progress** comes from the packer's own progress bar, which it prints into its log; the card and the Activity bar show it as a percentage.
- **A build that stays on "waiting"** means the runner has not picked the job up. `docker logs <container>` says why: at startup it prints a setup check (kit found, Wine set up, kit approved, ShadowPKG's config folder and each library mounted), and it reports once any job it cannot see, whether that is because `builds.json` is missing (ShadowPKG's own `/config` must be mapped, and that same folder mounted here at `/spkg`), the job's library is not mounted here at the same path as in ShadowPKG (the log names the path to add), or it is at a different path and `LIBRARIES` does not say where.

## What a package says about itself

Release names are rarely much help — `UP9000-CUSA47431_00-SCUS971980000000-A0107-V0100-CyB1K.pkg`, or worse, `NBA 2K16_1.pkg`. Every package carries the real thing inside it, in a `param.sfo` entry in its own table, and ShadowPKG reads it: the **title**, the **content ID**, the **version**, and whether it is a **game**, an **update** or **DLC**.

That costs three small reads — the header, the entry table, then `param.sfo` — no matter how big the package is, and they go through the same byte runs the file is served from. So a package sitting inside a stored `.rar` is read in place, without extracting it, and one split across volumes is read across the join.

The title leads each row and the file name moves underneath it, next to the title ID and anything that got in the way. Searching matches the title, the title ID and the content ID as well as the path, so `crash team racing` finds a release named after its content ID, and `CUSA13795` finds the game, its updates and its DLC together. Trademark marks are ignored on both sides, so you don't have to type `™`. Folder names are searched too.

The chips after a title read: `game`, `patch` (an update) or `DLC`; the version; `FW 9.50+`, the firmware it was built for, where the package says; `PS5` or `PS3` (a PS4 package shows none); `unconfirmed`, when the package has not been read yet, usually because it is still being written, so its ID and title are a guess from the file and folder names; and `no title`, for a PS5 package that was read and gave none.

How much can be read depends on which console the package was built for, and that is taken from its header rather than its name or its folder:

| Header | Console | What comes out |
|---|---|---|
| `\x7FCNT` | PS4 | Everything — title, content ID, version, kind, required firmware, cover art. |
| `\x7FPKG` | PS3 | The content ID, which is in the clear in the header. There is no readable title. |
| `\x7FFIH` | PS5 | Title, content ID, version, kind (game or DLC) and cover art — a PS5 package's *body* is encrypted end to end, but its container entry table is not, and neither is `param.json` or `icon0.png` inside it. |

A PS5 package wraps the same `\x7FCNT` container PS4 uses natively, just inside an outer `\x7FFIH` image at an offset the header itself points to — reimplemented here from reading the format, not from any existing code, with credit to [LibProsperoPkg](https://github.com/SvenGDK/LibProsperoPKG) (SvenGDK) for documenting it. Only the license/DRM entries and the game's actual data are encrypted; the metadata never was.

**What a PS5 package is** comes from the content type in that container header, since there is no `CATEGORY` as on a PS4: `0x21` is DLC and `0x20` is a game (a full game, the small stub some releases ship in its place, or an app). That was worked out against ninety-odd real packages, not taken from a document, and it is what puts `game` and `DLC` chips on PS5 rows, orders a PS5 title as game then DLC, and lets a rename say what a package is. **No PS5 update package was available to look at, so none is labelled an update.** A value the app has not seen, or a `0x20` whose `param.json` cannot be checked, simply has no chip; and if a PS5 update turns out to share its game's content type, as a PS4 update does, it will read as a game until that is settled. The stored package details carry a schema number, and for this only the PS5 entries that had no kind were read again.

Where the package can't say, a release named after its content ID still gives up which game it belongs to, and the app marks that as coming from the name rather than from the package. Anything whose header isn't one of the three is reported as not a package — an encrypted console dump, say — rather than as damaged.

Select one package and **Info** for everything above in one place, plus its cover art when the package carries one — `icon0.png`, read straight out of the file the same way the title is. For a PS5 package with a title ID (`PPSA` and five digits), Info also has a **Look up updates on PROSPEROPatches** link to that title's page on [PROSPEROPatches](https://prosperopatches.com), a third-party tracker of official PS5 updates, which opens in a new tab; ShadowPKG itself makes no request to the site for it. Info also has a **File** section with the file's own details (size, dates, attributes, where it is, what is using it, an on-demand SHA-256); see [Other files and Info](#other-files-and-info).

**Firmware.** A package or a game dump carries a `FW 9.50+` chip after its version, and **Info** has a *Firmware* field. On a PS4 package it is the package's own `SYSTEM_VER` (shown in hex in Info: `0x09508000` is 9.50). On a PS5 package, or a PS5 dump, it is the `sdkVersion` in its `param.json` — the firmware the game was built against, which is the number a release's `9xx` / `5xx` tag names — read from the package when its `param.json` is in the clear, and from the dump's `sce_sys/param.json` for a dump. A PS5 title also asks for a second, usually higher number (`requiredSystemSoftwareVersion`, what Sony's own installer insists on: a `3xx` game can ask for 7.40); it is not the chip, but the tooltip and Info give it. It is a hint and nothing more: no send is ever held back on it. It shows only where the file says — a PS4 package whose `SYSTEM_VER` is zero, and a PS5 package whose `param.json` is encrypted, show nothing — and **it is the firmware the release was built for**: a backported release does not update it, so a backport still reports the firmware it was built for rather than the one it now runs on.

The **version** on a PS5 package or dump is its `contentVersion` (`02.001.010`), which moves with every update, and not its `masterVersion`, which stays at the original build's `01.00`. It appears as a chip beside the name, on package rows, dump folders and the dump's card. The stored package details carry a schema number, so when this changed only the PS5 entries were read again.

Results are kept in `packages.json` in the config folder, keyed by size and timestamp, so a restart costs nothing and a file that is still being written is read again once it settles. They are filled in by a background queue that stands aside while archives are being scanned, since the two want the same disks.

## One game and everything that belongs to it

A game, its updates and its DLC all carry the same title ID, so that is what gathers them. Searching for a game you own three copies of gives you one row instead of twenty-seven:

```
▸ Crash™ Team Racing Nitro-Fueled            CUSA13795
  3 games · 3 updates, newest v01.21 · 10 DLC · 61.7 GB · 10 duplicates
```

Open it and the parts are in the order that makes sense rather than the order the sort asks for: the game, then its updates newest first, then its DLC. Groups and loose packages are sorted against each other on the same terms — a group stands on its own title, its total size and its newest file — so **Largest first** still means something.

A group only forms where there's more than one package, so a library with one file per game looks exactly as it did. Turn it off with the **Group** box next to **Sort**; the choice is remembered per device.

**Duplicates are counted on the content ID and the version together**, not the version alone. Every DLC a game has is version 01.00, so counting by version alone would call ten different add-ons ten copies of one. By content ID and version it reads true: three copies of the base game and three of the same update in one release folder is a real thing worth seeing.

It's also worth knowing what this makes visible. A folder called `Elden Ring V1.15` holding `01 BASE` and `02 UPD` will say **2 copies of patch v01.15** — because both files report themselves as updates, and the base game isn't there at all. The file name said otherwise. The [Duplicates](#duplicates) finder doesn't take the same bait: two files of very different sizes are never ticked as extra copies of each other.

## Renaming a package

Select one package and **Rename**. **New name** is already filled in with the default format below, so **Rename** as it stands gives that name. **Name it from the package's own details** (folded on a phone) shows what the package says about itself (its title, title ID, version, kind, region and platform) and offers other ways to build a name from it. Each one is shown with the name it would give for *this* package, so picking is a matter of looking:

```
Crash Team Racing Nitro-Fueled - Nitros Oxide Edition Content DLC CUSA13795.pkg     Title Kind vVersion TITLE ID   (the default)
Crash Team Racing Nitro-Fueled - Nitros Oxide Edition Content [CUSA13795].pkg       Title [TITLE ID]
Crash Team Racing Nitro-Fueled - Nitros Oxide Edition Content [CUSA13795] [DLC].pkg Title [TITLE ID] [Kind] [vVersion]
CUSA13795 - Crash Team Racing Nitro-Fueled - Nitros Oxide Edition Content.pkg       TITLE ID - Title
UP0002-CUSA13795_00-CTRDELUXEPACK001.pkg                                            Content ID
```

There is also *Title (Region) vVersion*, *Title only*, and **Your own pattern**, written from the pieces `{title}` `{titleId}` `{version}` `{v}` (the version with a v in front) `{kind}` `{region}` `{contentId}` and `{platform}`, each one a button so nothing has to be typed from memory. A piece the package doesn't have is left out with the brackets around it, so `{title} [{titleId}] {v}` never leaves an empty `[]` behind. **Options** turns spaces into underscores, dots or dashes (the scene's way of naming), makes the letters lower or upper case, and leaves out version 01.00 (which every DLC has) and the word *game*. The default is what the app has always offered, and the choice is remembered on that device. Renaming several packages at once uses the same format, with a list at the top to change it.

You can still type any name instead: it is used as you type it, and refused if it holds `< > : " | ? *` or a control character, or ends in a space or a dot. A name built from the package keeps letters and digits in any script, so a Japanese title survives, and drops the characters a Windows share won't take.

**The link a console is given comes from the path**, so renaming changes it: any link already handed out for the old name stops working. A send being *held* for a PS4 whose installer is not open is the exception: it follows the file to its new name (and is saved that way), so it still goes through when the app opens instead of failing for want of the old file. For that reason a package a console is downloading **right now** is refused rather than renamed out from under it — the transfer would otherwise die on its next range request with nothing to explain why. One that's finished, or has gone quiet for fifteen seconds, is fine to rename.

Also refused: anything with a folder in it, a name starting with a dot, a changed extension, a name already in use, and a package inside an archive — that one has no name of its own to change, so extract it first. The library has to be mounted read/write, the same as extraction.

### Renaming several at once

Select more than one package and the button becomes **Rename N…**. It opens a preview rather than doing anything: every selected package with the name it has now, the name its own details would give it, and a tick on each one that will be renamed. Whatever cannot be renamed is unticked with the reason beside it: a name already in that folder, two packages that would be given the same name (the first keeps it), a package a console is downloading right now, one inside an archive, one that has no title read yet, or one that already has the name. Names that differ only in case count as the same, since a library is often a share. Untick any you would rather leave, and the button counts what is left.

**Rename N** then does them, and the dialog stays open to say what happened to each one. It is never all or nothing: a package that fails (a file that appeared in the meantime, say) says why and the rest are still renamed, and the ones that could not be stay selected. What was read about each package comes along with it, so nothing is read again, and the list is rebuilt once at the end. A batch is capped at 200 at a time. Every row is keyboard reachable: Tab to a row, Space or Enter to tick it.

## Deleting a package

Select one or more packages and **Delete**. Nothing happens on that click — it opens a dialog listing every package selected, by title and file name, with the total size, and a plain statement that this can't be undone: the files are removed from disk, not moved anywhere. Only a second, deliberate press on **Delete permanently** inside that dialog does the work.

Every row in that dialog has its own checkbox, and a header row selects or deselects everything shown. Deciding you want to spare one file doesn't mean cancelling and hunting for it in the main list — untick it right there, and only what's still checked gets deleted.

Batches are handled item by item, so one package that can't be deleted doesn't block the rest of the selection. Refused for the same reasons renaming is: a package inside an archive has no file of its own to remove (extract it first; once its packages are out, the archive is deleted from its own row, see [Archives](#archives)) — and a package a console is downloading **right now** is left alone rather than pulled out from under the transfer, until it finishes or goes quiet. The library has to be mounted read/write.

If a batch partly fails, the dialog closes on whatever succeeded and the rest is reported in the selection tray, still selected, so you can see what's left and decide whether to try again. If nothing at all could be deleted, the dialog stays open and says why.

A send held for a PS4 whose installer is not open is dropped along with the package it was waiting to send, since there is nothing left to hand over; the page does not say so, but the log counts them and the reply to `POST /api/delete` names the console.

## Moving and copying

Select one or more items and **Copy** or **Move**. Both open the same dialog: a summary of what's selected, then a destination picker — any library, or any [FTP-connected console](#ftp-connected-consoles) — with the same folder browser used everywhere else, so the destination can be any folder in any of them. Source and destination can be any combination of local library and FTP console: local-to-local, local-to-FTP, FTP-to-local, or FTP-to-FTP. The dialog opens pre-pointed at wherever a Move or Copy from this library last actually went — a per-browser memory, like the theme, so sending a stream of finished builds to the same place doesn't mean re-navigating the folder picker every time; picking a different destination and starting a transfer updates it for next time, and it's checked against the real library list before being trusted, so one that's gone since just falls back to nothing pre-selected.

**Existing name at the destination** decides what happens to a clash: **Skip it** (default), **Overwrite it**, or **Keep both** (adds a number). **Also verify byte-for-byte (checksum)** checks a full hash of the copy against the source instead of just its size — slower on a large package, off by default; size is always checked either way, on every file, win or lose.

A **Move** copies first and only removes anything from the source once every file in the transfer has been copied *and* independently verified — the copy step throws before returning if a destination file's size (or checksum) doesn't match, which stops the whole job before a single source file is touched. A cancelled or failed move never reaches that removal step. Each file is written to a hidden temporary name first (or checked against a real destination listing, on the FTP side) and only counted as done once that's confirmed, so a job that stops partway never leaves a half-written file passing as finished. A folder right at an FTP connection's own root needs an extra tick — **I understand, start the move** — the same depth-based confirmation [FTP-connected consoles](#ftp-connected-consoles) uses elsewhere, because there is no reliable way to tell a game folder from something more sensitive that shallow on a console's FTP root.

The transfer runs as a background job, one at a time, with its own bar and **Cancel**; progress shows in **Activity** alongside downloads, extractions and builds. Too large to preview in one pass — a huge folder tree, or a share that's slow to walk — is refused up front rather than started and left to run forever.

## History

Finished downloads and extractions drop out of the live list in **Activity** after ten minutes — an hour if one never finished — to keep it small enough to be worth polling. **History**, a button inside Activity, is the record of what happened before that: downloads, sends (Sent or Failed, and whether the console came for the file), extractions and builds, kept on disk, so a restart doesn't lose it either. It keeps the last 300 entries and shows the newest 150 at a time, with **Load more** underneath once there's more to show. A filter box (matches the name), a kind dropdown (downloads, sends, extractions, builds) and a console dropdown narrow it down — each one starts the list over at the top rather than filtering what's already loaded, so "did I already send this" or "when did I last build X" is a filter and a glance rather than scrolling past everything else first.

Every entry says how long it took, and its **Details** (folded) give the clock time each part began and ended. A **send** shows when it was asked for, how long it waited in line behind the ones before it, when the console's turn began and how long the console took to say yes, then when the console began and finished downloading it and at what speed. A **download** shows its start, its end, its size and speed, and how many requests were cut short; one that never finished shows how much arrived and how long it was active. An **extraction** shows how long it waited for its turn, how long it ran, the tool that did it, and how many packages came out. A **build** shows how long it waited for a builder and how long it ran, and, from the container builder, how long each stage took (getting the kit ready, copying the dump to the builder's disk, making the package list, packing, copying to the library) with its share of the total, and the machine's figures: cores used, peak memory, disk speed, what limited it. Entries made before this was added, and builds from a builder that does not report stages (the Windows one), show what they have and leave the rest out.

Every entry says what it was, whether it finished, and **Open folder** jumps straight to where the file landed or was going — even for a package read out of an archive, which opens wherever the archive itself sits, since there's nothing to browse inside it. A download that never finished is recorded too, marked incomplete, rather than just disappearing when it's forgotten.

## Sending a batch

Send hands the whole selection to the server in one request (`POST /api/send`) and the server works through it: one package at a time per console, in the order given, through the same checks as a single send, each one waiting for the console to finish downloading the one before it (a PS4 only has to have started it), and the line moves on after ninety seconds with no progress. A send takes at most 500 packages; select fewer if the page says so. The page only watches. The rows say where each package is (*waiting in line*, *sending*, *queued on PS5*, *PS5: 63%*, *downloaded by PS5*), **Activity** shows the line and can **cancel what has not gone yet** (a package already with the console is the console's now; there is no call to take it back) and **Send the N that failed again** once the batch is over. A restart of ShadowPKG forgets packages not yet handed over; the ones the console has accepted carry on by themselves.

Once the console has begun fetching every package of a batch that was handed over, the batch's own card in Activity is left out: the download rows say the same thing, and two cards for one send looked like a fault. A batch card stays for anything that needs a word (waiting in line, held, failed, *already sent*, cancelled), and for a send the console has not started on yet.

**Order.** When every selected package says what it is, the dialog sends them as a console needs them: the game, then its updates oldest first, then DLC, and says so. If any package does not say (a PS3 package, one not read yet, or a PS5 one the app has no label for), the order you picked is kept, and the dialog says that instead. A group has **Game + newest update**, for the usual case of wanting those two and not every copy and every older update. The same package twice in one send (the same content ID and version, as in three folders of a real library) is left out, visibly, with a box to tick if you meant it. A package that is already on its way to that console (in another batch, or sent and not yet downloaded) is skipped by the server and said so, however it was asked for; one that went quiet part way (*paused*), or that the console never asked for, can be sent again.

**What the console did with it.** A console that accepts a send has only said it received the request. ShadowPKG watches whether it then comes for the file: *waiting*, then the download's percentage, then *downloaded* (never "installed": the installers do not say). A console that has not asked for the file after about ninety seconds (three minutes at the latest) is shown as *accepted it but has not asked for the file yet*, with a suggestion to look in its Downloads list or send again. That is not shown as a failure, because a busy console can start late. The history entry records how it stood when the console's line moved on after ninety quiet seconds: *downloaded*, *had not asked for the file when ShadowPKG stopped waiting for it*, or *the download started, then went quiet*. Download progress is written to `transfers.json` every fifteen seconds and when the app stops, so a restart in the middle of an install picks the transfer up where it was instead of counting again from zero and ending in a false "Incomplete".

**Not sent twice.** Only a request that never reached the console (refused, unreachable) is repeated. A batch to a console that does not answer stops after three in a row instead of trying every package (Activity offers to send the rest again). A reply that is merely slow may already have queued the install, so it is reported, with a note to look in the console's Downloads before sending again, rather than sent a second time. A console that could not be reached is not tried again for every package behind it for a minute. A PS3 package is refused before any request is made to a PS5 or PS4 installer.

**Send again.** A failed send, one the console never asked for, one that started and then went quiet, or an *Incomplete* download has **Send again** in History. For an *Incomplete* download it asks first if the same file is still listed as paused or downloading on that console; a send goes at once, and is skipped if that package is already on its way.

**A package the console already has.** A package this console has already finished downloading is not offered to it again: a console handed one it already has can refuse it, and its installer then stops taking further requests until its download list is cleared. The check is on ShadowPKG's own history of sends to that console (the same file at the same size, or the same package under the same file name in another folder, matched on content ID, version and size), so it holds across restarts for as long as the entry is among the last 300 in History. The row in Activity says *already sent before, not sent again*, the batch is tagged **Already sent**, and nothing is sent to the console. If you removed the package from the console and want it back, **Send it again anyway** in that Activity row sends it. A send that failed, was never asked for, or went quiet part way is not a finished one and can still be sent as before. A send the console accepted but has not finished (waiting, never asked for, or gone quiet) may still sit in the console's own download queue, so the Send dialog puts a warning under that package, the row's status line says so, and History's **Send again** asks first: sending it again there can make the console refuse it and stop taking further requests until its Downloads list is cleared.

**A download that stops a hair short of 100%.** A console can have the whole file and still leave ShadowPKG's record a little short of it: it kept part from an earlier try and asked only for the rest, or the app was stopped without a clean exit and lost the last few seconds of what it had written down. From the server's side that looks the same as a console that gave up, and the row used to sit on *Paused* with the next package in a batch waiting behind it. What tells them apart is how the last request ended: a console that gave up dies part way through one, while one that has what it needs finishes its last request in full and stops asking. So a download that has been quiet for 30 seconds, with nothing open, whose last request was served in full and that reached the end of the file, with no more than 5% never asked for, is taken as finished (and 60 seconds and 1.5% when the end of the file was never asked for). When what was never asked for is only a small trailing piece (under 1 MiB and under 2% of the file, as with a small package fetched in 64 KiB steps whose last part is never requested), five seconds of quiet is enough. It shows as Finished, History says how much was never requested, and the next package goes. One that was cut off, or is missing more than that, stays Paused; the row says how much was never asked for and where it starts, and the log gets one line about it ("download quiet short of the end…") with the gaps and how the last request ended. A console that turns out to have been wrong just asks again and is served as ever.

## Sending to a PS4

> **Work in progress.** PS4 support is newer than the PS5 support and is being built up. What works today is **Remote Package Installer** (below), and it has been tested against a stand-in for the app, not yet on a real PS4 beyond its recognition and health check. Other PS4 installers are not supported yet; the list is under **Not supported**, and **Adding another installer** says how to add one. The main gap today is that RPI is an app that has to be open on the PS4 (see **Sending while the app is closed** for how ShadowPKG softens that); an installer that runs as a payload avoids it, and supporting one is the most useful thing to add.

A PS4 cannot take an install command by itself. It needs a small app on the console that listens on the network and hands a link to the PS4's own background downloader. That app is **Remote Package Installer** ("RPI", originally by flatz), and ShadowPKG speaks its protocol: it gives RPI a link, the PS4 downloads the package from ShadowPKG and installs it in the background, the same as a PS5.

**What the PS4 needs**

1. **A homebrew enabler that allows fake packages.** On firmware 9.00 and newer that is usually **GoldHEN**:
   - 9.00: GoldHEN 2.3 (the last non-beta release) or 2.4b18.
   - 9.60, 10.00/10.01, 10.50, 10.70/10.71, 11.00: GoldHEN 2.4b18, from [its GitHub releases](https://github.com/GoldHEN/GoldHEN/releases).
   - 9.03/9.04 and 11.02 to 13.52: only the later 2.4b18.x betas, which are distributed from the developer's Ko-fi page rather than GitHub.
   - The open-source [Scene-Collective ps4-hen](https://github.com/Scene-Collective/ps4-hen) also has the patches RPI needs, but there are no reports of RPI on it yet.

   How the console is jailbroken is outside ShadowPKG; follow the enabler's own instructions. Every GoldHEN release lists "Remote Package Install" among its features, which is this.
2. **RPI installed on the PS4**, once, with GoldHEN's Package Installer (from USB or `/data/pkg`). The builds:

   | Build | Port | Notes |
   |---|---|---|
   | flatz original, "Remote PKG installer" 1.02 (title FLTZ00003), from [PKG-Zone](https://pkg-zone.com/details/FLTZ00003) / the Homebrew Store | 12800 | The one most people use. Reported working on 9.00 and 11.00. |
   | [njzydark PS4RPI](https://github.com/njzydark/PS4RPI/releases) 1.01/1.02 | 12801 | Fixed an install error some saw on 9.00. |
   | [mk990 PS4RPI](https://github.com/mk990/PS4RPI/releases) v1.08 and later | 12800 | Newest (2026) and the most robust code, but few reports yet. v1.03 to v1.07 used 12801. |
   | Backporter OOSDK port 1.0 | 12800 | Reported to fail on 9.00; avoid. |

   Run one at a time; they share ports. These are third-party builds, so check what you download.
3. **RPI open, in the foreground, when you send** — and until the PS4 shows the download has started. The PS4 pauses apps in the background, and the download's first step is fetched from RPI itself. After that you can leave RPI and the download carries on. If the PS4 later says "the connection to the server has been lost", open RPI again and resume the download from Notifications.
4. **The PS4 able to reach ShadowPKG**: same network, and ShadowPKG's address (the setup panel's *Public address*) set to the server's LAN IP and port, not a name like `tower.local`.
5. **PS4 packages.** A PS5 package cannot be installed on a PS4; ShadowPKG refuses to send one.

**Adding it in ShadowPKG**

- **Discover** (in *Your consoles*) finds it while RPI is open: it looks on port 12800, and on 12801 for the builds that use it. It shows as "Remote Package Installer (PS4)". It searches the /24 networks the server is on, the one `PUBLIC_BASE` is on and the ones your saved consoles are on; in Docker's default bridge network the server's own network is Docker's, so set `PUBLIC_BASE` first, or add the console by hand, if it finds nothing.
- **A PS4 whose app is closed cannot be discovered**, because the app is the only thing on the PS4 that listens. Add it by hand instead: *Add a console*, its IP address, and tick **"This is a PS4 (Remote Package Installer), even if the app isn't open"**. Sends to it are then held until you open the app, even if it has never been seen. (Discover's **Use this** ticks the box for you.) The same tick is in the console's **Edit** form.
- **By hand:** *Add a console* with the PS4's IP (port 12800 is assumed). If your build uses 12801, ShadowPKG notices and moves the console there by itself, or type `ip:12801`.
- **Test** checks the whole path: RPI asks ShadowPKG for a test link that does not exist, fails on it, and installs nothing. "Healthy" means the PS4 can reach ShadowPKG.
- Then send as with a PS5. A package already installed is reported as such rather than as sent, and the PS4's own error codes (not enough space, stuck downloads) are translated.

**Sending while the app is closed.** RPI only answers while its app is open. Once a console has answered as RPI, ShadowPKG remembers that, and a send to it while the app is closed is **held** instead of failing: Activity lists it under the console with an *N waiting* tag and a note to open Remote Package Installer, with **Remove** on each and **Try now**. The moment the app is open, ShadowPKG hands the held sends over by itself, one after another, and Activity says **"you can leave Remote Package Installer"** once the PS4 has actually begun downloading the last one. So the app only has to be open for the few seconds a batch takes, not for the whole download. Held sends are kept across restarts of ShadowPKG in `held.json` in the config folder, follow a package that is renamed and are dropped if it is deleted, and nothing is sent to the console until its installer answers. ShadowPKG looks for the app every 20 seconds while something is waiting. Otherwise it only checks when a page asks for the console's status, and then at most every three minutes, because most RPI builds keep a thread for every connection they are given. An automatic send after a build is held the same way.

**One PS4 is one profile.** RPI builds listen on port 12800 or on 12801, and one PS4 answers on only one of them. ShadowPKG treats a console at the same address on either port as the same PS4: adding it a second time, or editing one to the other's address, is refused with a message saying which saved console it is, Discover marks an app found on the other port as the PS4 you already have (with **Use this port** to update it, not a second profile), and a PS4 whose app has moved to the other port is followed there by itself.

**Several PS4s, changing addresses.** Each PS4 is its own console in the list, like PS5s, and can be added by hand or with **Discover** (which lists every PS4 whose app is open and marks the ones you already have). Each keeps its own waiting list, so opening the app on one hands over only what was sent to it. A PS4 whose app is closed shows as "Remote Package Installer is not open" (a grey dot, with no warning) rather than as broken. If a console changes address (a new DHCP lease), ShadowPKG follows it when there is only one it could be: either an unknown address starts downloading from ShadowPKG and answers as the one missing console of its kind, or a search of your networks finds it (every five minutes for a PS5, every fifteen for a PS4, and a PS4 is only adopted when no other PS4 is missing). With several PS4s the safest thing is to give each a fixed address (a DHCP reservation in your router) and, if one does move, change its address in **Edit**; **Discover** shows where the app answers now. **Find it** is not shown for a PS4 running Remote Package Installer.

**How it works.** RPI answers `POST /api/install {"type":"direct","packages":[url]}` only after it has read the package's header, icon and details from the link, so a send can take several seconds. If the PS4 has not come for the file 25 seconds after accepting it, ShadowPKG asks RPI to start the task, which one build needs. ShadowPKG recognises RPI by the error it gives for its home page, since it has none, and checks on it only every few minutes: most builds keep a thread for every connection they are sent, and too many make them stop answering.

**Not supported**

- **OnionHEN's DPI v2 plugin** runs on a PS5 and receives files uploaded from a browser; it has no way to be handed a link.
- **etaHEN DPIv2** is a PS5 installer (supported as such).
- **ezRemote Client** has a URL-install call, but its current release (2.05) reports success even when nothing was queued, and its background install stalls at 0 bytes (its issue #50). Worth revisiting after its next release.
- **PS4PackageInstaller** ([paoloviola/PS4PackageInstaller](https://github.com/paoloviola/PS4PackageInstaller)), a payload that people load themselves, has its own API on its own port and is **not built into ShadowPKG**: it does not appear in Discover and ShadowPKG does not send to it. That is left open for anyone who wants it; its API is documented in its own repository, and **Adding another installer** below is where a driver for it would go. Loading such a payload onto a console is a separate, by-hand act — see [Sending a payload](#sending-a-payload).
  - **Why it is worth adding.** It is a payload, not an app, so unlike RPI there is nothing to keep open or in the foreground on the PS4, and nobody has to be sitting at the console: it is loaded from a PC or phone on the network, then takes install requests over HTTP and hands them to the PS4's own background downloader. That removes the biggest limit of the RPI route, the need to open the app on the PS4 for every batch. The catch, from its own source, is a **60-second listening window**: it stops listening once 60 seconds pass without a request (each request restarts the count), so it is loaded just before sending rather than left running, and has to be loaded again for the next batch. Source, releases and its own documentation: [github.com/paoloviola/PS4PackageInstaller](https://github.com/paoloviola/PS4PackageInstaller) ([releases](https://github.com/paoloviola/PS4PackageInstaller/releases)).
- **GoldHEN's port 9090** (BinLoader) runs any program sent to it; [payload sending](#sending-a-payload) only ever uses the loader port saved on the console, so it reaches 9090 only if you set that port to 9090 yourself. Its **FTP server on 2121** is for copying files, not an install API.
- **FPKGi** and the **Homebrew Store** pull from a catalogue rather than being sent links; not supported for now.

**Adding another installer.** An installer is a small object in `DRIVERS` in `server.js`, and ShadowPKG only ever acts as an HTTP client of it:

- `label`: the name shown in the console list, Discover and Test.
- `matches(html)`: recognises the installer from its home page (`GET /`). One with no home page (as RPI) is recognised in `detect()` instead, by the way it answers to a request that changes nothing.
- `install(host, pkgUrl)`: asks it to fetch the link, and returns `{ok, status, reply}`. Read replies leniently; installers are sloppy about JSON.
- Optional: `platforms` (which package kinds it takes, so a PS5 package is not sent to a PS4), `retryAfter(error)` (which failures mean the request never reached it, so are safe to try again), and `noReply` / `rejected` (what to tell the person when it stays silent or refuses).

Test it against a stand-in server that answers the way the real one does, as the RPI checks do, and where a console can be found without its app running, add it to `findConsoles()` so Discover lists it and to `savedAs()` so one console is never saved twice. A driver is a client of an installer that is already running on the console; putting a program on a console is a separate, deliberate act ([Sending a payload](#sending-a-payload)), never something a driver does.

This support was written from the RPI builds' source code and tested against a stand-in that answers the same way, not on a real PS4. If a send behaves oddly, the **Test** result and `GET /api/log` are the first things to look at.

## Sending a payload

A jailbroken console is usually brought to life by sending it a payload — an `.elf` (etaHEN, elfldr, a loader chain) or one of the other forms a given loader takes. Each console in **Your consoles** now has a **Send payload** button for exactly that.

It opens a small dialog with three ways to choose one. **Stored payloads** are files kept inside SPKG itself, in a `payloads` folder in the config folder — pick one and it goes, and it is there again next time, from any device. **Library** browses your mapped libraries the same way as anywhere else (only `.elf`, `.bin`, `.js`, `.lua` and `.jar` are listed). **Or send one from this computer** takes a file from the device you are on; press **Save to SPKG for later** and a copy is kept in the stored list, so a payload uploaded once is one click away after that. Saving never sends anything by itself, and **✕** on a stored row removes it (only the copy in SPKG — nothing else is touched).

**Send payload** then writes the chosen file to the console's own IP on its **loader port**, as raw bytes over TCP, which is what elfldr and the like expect. The port is set on the console: **Edit → Payload loader port**, default **9021** (elfldr, and most ELF loaders). The dialog can override it for one send without saving, which is what you want for the other forms — `.js`, `.lua` and `.jar` reach the port their own loader listens on (typically `.js` 50000, `.lua` 9026, `.jar` 9025).

This is the one place ShadowPKG puts a program on a console, and it is a plain one-way write. "Sent" means the bytes left the server and the connection did not fail — the loader itself may still reject the program on the console, and ShadowPKG cannot see that. It never runs by itself: nothing goes out until the button is pressed. It installs nothing, and it changes nothing else on the console. A file sent from this computer is not written to disk anywhere; the bytes go to the console and are then dropped.

It is not the same thing as a driver under **Adding another installer** above: a driver is a client of an installer that is already running on the console, while this starts one. And it is always a deliberate press — nothing here sends a payload on its own, on a schedule, or after a send.

## FTP-connected consoles

A jailbroken console's homebrew FTP server (goldhen/etaHEN) can be added to a console's profile, in **Edit** under **FTP (for a jailbroken console)**: host (defaults to the same address as the DPI install address), port (2121 and 1337 cover most setups — quick preset buttons, not a live probe, since there's no way to test a port without a saved connection to try it through), and a user/password (blank for anonymous, which many goldhen/etaHEN setups are). A profile with no FTP host set simply has no FTP source — this is entirely separate from, and optional alongside, DPI sending.

A console with FTP set up shows as its own entry in the library dropdown, browsable exactly like a local library — folders, other files, Rename, Delete, and now [Copy/Move](#moving-and-copying) to or from it. This reuses the same folder view, not a parallel one, but it is a genuinely different, less provable connection underneath: there is no local disk to prove a path never left where it should, no atomic rename most embedded FTP daemons offer, and no real symlink information to check. So FTP gets its own, narrower safety rules, stated plainly rather than implied:


**Installed games.** In the library menu, a console over FTP has an **Installed Games** button beside its FTP chip. It lists what that console has installed: every game (PS5, PS4 and anything else installed, without the console's own apps), with its title ID, the version installed, its size and where it is (Internal, M.2, Extended USB), an **update installed** chip when an update package is installed for it, and, for a game with DLC, a chip with how many (*6 DLC*): click anywhere on that game's card (or press Enter on it) to open or close the list of its DLC, each with its name and version. A card stays open while you filter or refresh, and a filter that matches a DLC name opens the card it is in. DLC whose game is not installed is listed at the end under its title ID, already open. When your libraries hold a newer version of a game (an update or a copy, from what ShadowPKG has already read), a **newer in library** chip says which, and opens that folder. A filter box searches names, title IDs and DLC names; with **Covers** ticked each game shows its icon. An icon is fetched once: from a package of the same title ID in your libraries when there is one (fast, local), otherwise from the console over FTP, then kept in the config folder (`icons/`, a few MB for a console with ~90 games; about 5 seconds the first time for all of them, about 1 second after) and kept by the browser for a week. A reinstall (a new install time) gets a fresh icon and the old file is removed; a title with no icon is not asked about again for ten minutes. **Refresh** reads the console again (an answer is otherwise kept for two minutes).

How: the console keeps what is installed in two small SQLite files, `/system_data/priv/mms/appinfo.db` and `addcont.db`. ShadowPKG copies them over FTP into a temporary folder, reads them with the SQLite module built into Node (22.13 or newer; the Docker image has it), and deletes the copies; it lists the consoles' `patch` folders to see which games have an update installed. Nothing on the console is changed. It needs an FTP server that reaches the device root (etaHEN's does); one that does not gets a plain error. `GET /api/ftp/installed?src=` gives the same list as JSON (`&refresh=1` to read it again).

**zftpd.** If a console's FTP port is [zftpd](https://github.com/seregonwar/zftpd) (a console FTP server payload that also answers HTTP on the same port), ShadowPKG notices: it asks that port two things, `GET /api/status` and `GET /api/mounts` (when the page loads, and again when the library menu opens), and a console that answers as zftpd has its **FTP** chip replaced by a **zftpd** one everywhere it is shown (the library menu, the Send dialog, the Move and Copy destination list), with the drives that are really connected and how much is free on each (*usb0: 11.7 GB free of 29.8 GB · ext1: 383.7 GB free of 931.5 GB*) under its name. The same line is in the Installed Games window. A console running another FTP server (etaHEN's, say) does not answer those as JSON and shows nothing different; the answer is kept for 20 seconds (a minute when it is not zftpd), so it is not asked often. Those two GETs are all it sends by itself: nothing is ever loaded on a console automatically, so zftpd has to be started by you (a payload you send by hand through [Send payload](#sending-a-payload) is the one way and the only way, and it is your press that does it). Eject, Notify and Download as ZIP (below) are the same: each one only ever runs on a press, never on its own. The plain FTP features work with zftpd as with any FTP server (it speaks `MLSD`, `SIZE`, `MDTM`, `REST` and `APPE`) — on the one real device this was tested against, zftpd's HTTP side (`/api/status`, `/api/mounts`, `/api/notify`, `/api/system/disc`, `/api/system/eject`) answered reliably but its FTP control connection did not answer at all, so the plain file-browsing and server-side-copy features could not be exercised there; `GET /api/ftp/zftpd?src=` gives the same answer as JSON (`&refresh=1` to ask again).

**Copying and moving on a zftpd console.** When both ends of a copy or move are folders on the same console and its FTP port is a zftpd, the console is asked to copy by itself (zftpd's `CPFR` and `CPTO`): the data never leaves the console, so a game moved between its internal drive, M.2 and USB goes at the speed of its own disks instead of down one FTP connection and back up another. zftpd answers at once ("Copy started in background") and then says nothing more, so ShadowPKG watches the destination and counts what is there (the transfer's bar follows it) until every file is present at its exact size, twice running; empty folders are made too. A move removes the source only after that, and after the same second look at the destination every move gets. A copy that stops growing for two minutes fails, with the source left alone and what the console wrote still at the destination (zftpd has no way to be told to stop, so **Cancel** stops the watching, not the console). If the console will not start the copy, or when a checksum check was asked for, or when the source and destination are on different consoles or in a library, the copy goes through ShadowPKG as before. The job's message says *copied on the console itself* when the console did it. Switch it off with `ZFTPD_COPY=0` (or in Setup, Settings).

**A message on the console.** When a build finishes or fails, a console whose FTP port is a zftpd shows a short on-screen message (zftpd's `/api/notify`): *build finished: <name> is built …*. It goes to the console the build is being sent to, or else to every saved zftpd console; a console that is not a zftpd is never sent anything. A build you cancel yourself shows nothing. Switch it off with `ZFTPD_TOAST=0` (or in Setup, Settings). **Notify** in **Your consoles** sends a short test message by hand, the same way, so you don't have to wait on a real build to try it.

**Eject and drive space.** A zftpd console's free space shows under its name in the library menu and Installed Games, read from `/api/mounts`. **Eject** in **Your consoles** asks it to open its disc drive (`/api/system/eject`), hidden on a console with no optical drive. Some zftpd builds answer Eject only to their own web page, not to another program (a CSRF check their docs mention for any `POST` once upload support is on) — ShadowPKG never tries to obtain or forge that token, so on a build like that **Eject** answers with the console's own refusal, in its own words, rather than pretending the console didn't answer.

**Download as ZIP.** Browsing a zftpd console's FTP library, the selection tray gets **Download as ZIP**: the console itself builds the archive while it streams it (`/api/archive/zip`), so nothing is written there and ShadowPKG only relays the bytes. Only shown for a console confirmed zftpd, and only once something is selected.

**Staying out of the device root.** A console opens in its default folder (usually `data`), and the toolbar's *Data (default)* / *Device root* switch is the one deliberate way out of it. Going **Up** from the top of the default folder does not leave it: the Up button, the `..` row and Alt+Up stop there, and the names of any folders above it in the path are shown but are not links. Anywhere outside the default folder, the real root or a folder off it, a banner sits above the listing saying so: the root holds the console's system partitions, the check that refuses to rename or delete a known system name is not a complete guarantee, and a wrong change there can stop the console from starting. It has a **Back to Data (default)** button and a **Hide this warning…** button. Hiding asks you to tick that you understand the risk, then offers **Hide for now** (until the page is reloaded) or **Hide forever** (remembered on this browser). The box *Warn me when I am outside the console's default folder*, under an FTP folder's list, turns it back on with one click; turning it off from there goes through the same acknowledgement.
- A path is rejected outright if any segment is exactly `..` or `.` — never silently normalized away.
- A folder or file directly under the connection's own root (nothing above it) needs an extra confirmation — **I understand** — before it can be renamed, deleted, or moved out of, because there is no reliable way to tell a game folder from something more sensitive that shallow on a real console.
- A handful of system-partition-adjacent names observed on real hardware (`system`, `preinst`, `dev`, `host`, and others) are refused outright for rename/delete/move-source, with no confirmation able to override it — but this is a name check only. It cannot see through a folder that looks ordinary but is actually an alias or mount into one of those locations underneath — a real, reproduced gap, not a hypothetical one — and the delete-preview dialog says so before you ever confirm.

Uploading pushes a single file from a local library to the console over FTP; downloading streams a single remote file straight back to the browser as a save-as. Moving or copying a whole folder works the same way [Moving and copying](#moving-and-copying) does for local libraries, in either direction.

## Setup and network

The commonest question about this app is "why can't my PS5 connect?", and the answer is nearly always one of a handful of things. Rather than waiting for a send to fail, it checks them and says so, without filling the top of the page with warnings: the 📶 icon carries a count (red when something is wrong, amber for a warning), a short notice appears when something *new* goes wrong, and a strip under the header appears only for what stops a package being sent at all (no console set up, packages served from an address the console cannot reach, a library that is not mapped). The panel behind the icon has the full list:

- **Where packages are fetched from.** `PUBLIC_BASE` if you set it, otherwise the address you opened the page with. If that resolves to `127.0.0.1` or the Docker bridge, your console can never reach it, and the panel says which LAN address to use instead.
- **What addresses this server actually has**, with Docker's own bridge marked as the trap it is.
- **Each console** — answering or not, and which installer it's running. A console that answers but isn't running a DPI v2 page is a different problem from one that's asleep, and they're reported differently.
- **Each library** — mapped, and writable or not. Read-only means no extracting, renaming or deleting; sending is unaffected.
- **Each library's free space.** The library menu (when there is more than one library) carries a small line under each name, like "412 GB free of 4 TB · 812 GB in packages", and the panel repeats it. Under `LOW_SPACE_GB` (default 50) it also gets a quiet warning that counts on the icon and can be hidden for a day, like the others. Read the figures as a guide: they are what the share reports, on Unraid `/mnt/user` is the pooled share rather than the one disk that will take a file, and "in packages" adds up the packages in the list, which includes ones served from inside stored `.rar` archives, and not compressed archives, dumps or anything else on the disk.
- **Whether settings persist**, whether an extractor is installed, whether the log is being kept, and what's still being indexed.
- **Whether a password is needed**, as a plain note either way. It is information, not a warning, so it never counts on the icon.
- **Leftover unpack folders** from an interrupted extraction, with a button to review and remove them (see [Interrupted unpacks](#interrupted-unpacks)).

**Hide for a day.** A warning that does not stop sending (say, no extractor in the container when you never unpack archives) has a **Hide for a day** button in the panel. It stops counting on the icon and stops giving notices, on that browser only. It comes back after a day, or sooner if it gets worse (a warning that turns into an error), and **Hidden for a day: show again** undoes it at once. Problems that stop sending cannot be hidden. The notice is short and goes away by itself after a few seconds, is given once per new problem, and is not given while the panel is open.

The panel opens by itself the first time a browser loads the app, and not again — reopen it any time from the icon. It's a checklist rather than a step-by-step wizard: problems here are usually one mapping or one variable, they can be fixed in any order, and the same list stays useful long after setup.

**Copy support report.** Asking for help used to mean a screenshot of this list, the log in another tab and, for a build, a terminal command, which on a phone is close to impossible. The button at the bottom of the panel puts what someone helping would ask for into one text box: the checks with their levels, the app name, build, Node version and uptime, the addresses the server has, where packages are fetched from and why, whether settings are kept, each library and console (and the installer it is running), the builder's status and checks, and the last 150 lines of the log (60 of the builder's, once one has been seen). Anything else the diagnostics contain is included too. Nothing is sent anywhere: the text is put together in the page from what it already reads from the server, and it is shown in full before **Copy** puts it on the clipboard.

Two switches, both on every time the box opens, change what is shown as you flip them. **Mask IP addresses** turns a private address into its first two parts and its last (`192.168.x.230`), so consoles can still be told apart, and any other address into its last part alone. **Leave out file and folder names** turns folders and file names in paths and in the server's own log lines into `…` (keeping a file's extension), and extra libraries, which are named after their folder, into Library 2, 3 and so on. The container's own places (`/config`, `/games`) stay, since they are what makes a mapping problem readable. This is best effort: console nicknames, host names and game titles are not touched, so read the text before you paste it. `NOTIFY_URL` is never sent to the page, so it cannot be in the report. Over plain HTTP most browsers will not let a page use the clipboard; Copy then falls back to the older way, and if that is refused too the text is selected so the browser's own Copy can take it.

**Submit an issue.** Something wrong, or not clear? The first time the Setup panel opens by itself it has a box at the top, *Something wrong, or not clear?*, with a **Submit an issue** button; the same button is at the bottom of the panel for everyone, and the page footer has a link. It opens the GitHub issue form for the project in a new tab and puts nothing in the address. Press **Copy support report** first and paste it into the issue: it saves a lot of back and forth.

#### Options, patches, cancelling and the builder's log

- **Builder line.** Before you press Build the card says whether a builder is running for this library. The container writes a small `.shadowpkg-builder.json` at the library's root every 15 seconds; one that has gone quiet means no builder is running, and one that is online but not ready lists what is missing (kit not mounted, setup not run, kit not approved).
- **Quick validate** builds only the package list (about half a minute), reports how many files it mapped, and throws the scratch files away. It catches a bad dump before an hour of packing. The container builder only.
- **Options** on the card: compression (-4 to 9, the kit's default is 7) and PlayGo chunks (1 to 255).
- **Cancel build** stops a running build, kills the packer and removes its scratch folder and any half-copied package. The container builder only: the Windows builder does not watch for a cancel request, so its build carries on to the end. A build that is only waiting can be cleared instead.
- **Build a patch.** When the dump's folder also holds a `.pkg`, Options offers it as the base for a patch (the kit's `reference=`). The result is `<content ID>-patch.pkg` plus a `.remastered.pkg` companion, both copied into the library, or neither. The container builder only; the Windows builder refuses such a job.
- **Send when done.** Tick "Send to <console> when it finishes" and the finished package is queued to that console through the same checks and queue as the Send button, and the result shows on the card and in Activity. This happens on the server, so it works with the page closed.
- **Scratch clean-up.** The container removes its work folders for jobs that have been cleared at once, and for finished jobs after `WORK_KEEP_DAYS` days (default 2; neither the template nor the installers set it, so add it as a variable on the builder container to change it), at startup and hourly. It never touches a folder while a build runs.
- **Quiet hours.** `BUILD_QUIET_HOURS` on the container builder (comma-separated `HH:MM-HH:MM`, the container's own local time, a window may cross midnight: `23:30-00:30`) stops it from *starting* a new job inside those windows — for keeping a build from being claimed right before something like Unraid's Appdata Backup stops the container mid-way. It stays waiting and is picked up once the window ends; a build already running is not touched, since there is no way to pause the packer partway through, so the container should still be left out of anything that stops it outright during a window this can't see the end of. Shows in the builder's own checks (Setup, or `.shadowpkg-builder.json`) as an informational line, never a reason it's "not ready".
- **What limits a build.** While packing, the builder logs a line a minute: percent, GB written and MB/s, and what the container is using meanwhile (CPU cores busy of how many, memory and how much of it is file cache, disk read and write, and the share of time spent waiting on disk). When the build ends it logs the averages and which of CPU, disk or memory limited it, or that neither did, and the finished card says how long it took and how many cores it used. The figures come from the container's own cgroup and kernel pressure files, so they need nothing installed, and a figure the host does not provide is left out. As a rule of thumb: "CPU" means more or faster cores or a lower compression level would help and more memory would not; "disk" means a faster disk for the dump and the work folder would help; "neither" means the packer cannot use more of either, so more memory or cores will not speed it up.
- **The builder's log.** The container keeps `builder.log` in its config folder (`/config`, two files of 2 MB), so it is on the share and survives the container being recreated. A copy of the tail is put at each library's root, and ShadowPKG shows it at `/api/build/log`: use **Builder log** beside the builder line on a dump card, or in the setup panel next to **Open the log**. The Windows builder writes `watch.log` in its own folder instead.

#### DLC for another region

A DLC belongs to one game by its title ID, and the game's region is the first two letters of the content ID (`EP0001-PPSA20397_00-ULCQUEST00000001`: Europe, publisher 0001, title `PPSA20397`, and a 16-character label that names the entitlement). The US release of the same game is another title ID, so a European DLC installs under the wrong game and is never found by the US one. Select the DLC (only PS5 DLC packages in a local library), press **Change region…** in the selection bar, and each is rebuilt as the same DLC of the other release: the **label** stays, the region letters, publisher number and title ID come from the target game. Nothing is invented.

- **The target** is chosen from the other releases of the same game that the libraries hold (a game's name appears in its DLC's title, and the game's concept ID, which is the same in every region, confirms it: such a game is marked *same game*), or typed in as a region and a title ID, in which case it is used as given and marked unchecked. The dialog shows the file each DLC will be called.
- **Who builds it.** The container builder, with the kit's own publishing tool, the same two steps as a game: the package list with the additional-content volume, then the image. That tool writes the license entries (`license.dat` and `license.info`) a console needs to record the DLC as owned; a package made without them installs but registers nothing, which is why this is not done by editing the package. The job appears in Activity like any build (`DLC for US · content ID · from PPSA20397 · into <library>`), can be reordered and cancelled, and **Send to console when it finishes** is offered. A builder that predates this says so on the button (the page reads it from the builder's status file); the Windows builder does not do this.
- **What it makes.** ShadowPKG reads the DLC's own `param.json` and icon (both stored in the clear), switches the title ID, content ID and, when the target game says, its version-file link and concept ID, removes the two fields an additional-content package must not carry (`applicationDrmType`, `applicationCategoryType`), and stages the two files in a hidden job folder in the output folder. The builder points the project at that file (the kit's script regenerates it as if for a game), gives the package a random 16-byte entitlement key, which a DLC with no data of its own never uses, and packs it at compression 7.
- **Looking online.** Unless `STORE_LOOKUP=0` (or the Settings switch is off), the dialog has **Look online for other releases**. The server asks the PlayStation Store's page for the game's concept ID (the same in every region) in the US, EU, Japan, Hong Kong and Korea stores, reads the product IDs on each page, and lists every other title ID found, with the stores that show it and whether this DLC's label exists there (*has this DLC*). Choosing one builds with that region and title ID, like a typed target (the version-file link stays the source DLC's). Answers are kept for an hour. A release the store does not list for a region (a game never sold there) cannot be found this way: type it. `GET /api/build/dlc/online` does it for a script, and is refused (403) with the switch off.
- **Where the files go.** By default each rebuilt DLC lands in a new folder, `region change output`, next to the DLC it came from (made if it is not there), so converted packages never mix with the originals. The dialog's **Put the built files** menu offers two other places: *Beside the target game* (only when the target was picked from a library) and *Another folder…*, a library and a folder path in it (made if missing; empty means the top of the library; no `..`). The job's hidden `.shadowpkg-build` folder is made in the same place. `POST /api/build/dlc` takes `output`: `{"mode":"default"}`, `{"mode":"target"}` or `{"mode":"folder","src":"<library>","path":"<folder>"}`.
- **Unlockers only.** A DLC that ships data of its own (its image is more than a few MB) is refused: the data sits in the encrypted image and would have to be carried over as well.
- **A mixed selection.** DLC of different games (different title IDs) cannot share a target, so when the selection holds more than one game's DLC the dialog asks which game's to convert now; the rest stay selected. The region list leaves out the region the chosen DLC is already in, so a US target is missing when the chosen DLC are the US ones.
- **Refused up front** with a plain sentence: a package that is not a PS5 DLC, a target that is not a game, the same title (nothing to convert), a content ID already present in that folder, an unknown region, a title ID that is not `PPSA` and five digits.
- **Before sending.** If a DLC with the same content ID is already installed on the console, remove it there first: a console offered a package it already has can refuse it and then stop taking further requests until its Downloads list is cleared (the dialog says so).
- `POST /api/build/dlc` and `GET /api/build/dlc/targets` do it for a script (see the endpoints table).

#### Notifications

Set `NOTIFY_URL` on ShadowPKG (not the builder) and it posts a short message when a build finishes, fails or is validated, and says whether the package was sent. Cancelling a build yourself sends nothing. It works whether or not a page is open. With `NOTIFY_ON=builds,downloads` it also says when a download that ran more than two minutes has finished and when one has gone quiet part way for five minutes (once, with how far it got; it carries on by itself if the console asks again); `problems` gives only the second. A message still inside its minute of waiting when the app is stopped is sent first. A batch of small packages finishing together is one message, not ten. Examples:

```
NOTIFY_URL=https://ntfy.sh/my-secret-topic
NOTIFY_URL=https://discord.com/api/webhooks/ID/TOKEN
NOTIFY_URL=https://hooks.slack.com/services/...
NOTIFY_URL=https://api.telegram.org/botTOKEN/sendMessage?chat_id=12345
```

Anything else gets the message as a plain-text body with a `Title` header (ntfy, Gotify-style receivers); use `NOTIFY_FORMAT=json` for a receiver that wants `{title, message, text, content}` (Home Assistant webhooks and the like). The card's Options fold has **Send a test message** once `NOTIFY_URL` is set and `NOTIFY_ON` includes `builds`; `POST /api/notify/test` sends one whatever `NOTIFY_ON` says. Treat the URL as a secret; it is only used from the server and never sent to a page. A failed delivery is logged as the reason alone (which can name the host, never the path or a token in it).

## Who can reach the app

ShadowPKG is built for a home network and, by default, asks nobody for anything. It refuses one thing on its own, and two optional settings go further.

**Cross-site requests are refused.** Without this, any web page open in a browser on your network could make that browser post to ShadowPKG in the background: send a link to a console, delete a package, repoint `PUBLIC_BASE`. Every `POST`, `PUT` and `DELETE` now gets a 403 when the browser says it came from somewhere else: an `Origin` that is not this server's own address, the `PUBLIC_BASE` host or an `ALLOWED_ORIGINS` entry; an `Origin` of `null`; or `Sec-Fetch-Site: cross-site`. The log names the rule that fired. The page itself is unaffected. Scripts are too: curl and the builders send no `Origin`, and no `Content-Type` is required, so `curl -d '{...}'` works as before. Reads (`GET`) are never refused by this check. Behind a reverse proxy that rewrites the `Host` header, set `PUBLIC_BASE` to the public address, or list it in `ALLOWED_ORIGINS`.

**A password.** Set `ACCESS_PASSWORD` and the page, the API and `/files/` ask for a user name (`ACCESS_USER`, default `shadow`) and the password. A browser asks once and keeps the answer; for curl, add `-u shadow:PASSWORD`. A wrong password is answered half a second late and logged without what was typed, and an address that sends ten wrong ones in a minute is shut out for a minute, even with the right password, so guessing cannot be done in bulk (two people behind one address, such as a proxy, share that). The Windows builder needs the same two values in `builder.json`; the container builder is unaffected. The password is never shown anywhere, and the Setup panel only says whether one is set.

**One address.** `BIND_ADDRESS` makes the server listen on a single address of the machine, and the startup line says which. `127.0.0.1` means only that machine can reach it, which suits a setup where a reverse proxy runs beside it. That needs host networking: on Docker's default bridge network `127.0.0.1` is the container's own loopback and nothing outside could reach the app, so leave it unset there and publish the port to one address instead (see the table in [Configuration](#configuration)).

What none of this does:

- The cross-site check does **not** stop DNS rebinding, where a page gives its own name the address of your server and so looks like the server's neighbour. An unfamiliar `Host` name is logged once, as a first look, and nothing is blocked. The password does stop it.
- Package links (`/p/...`), the health-check probe (`/probe/...`) and `GET /healthz` (what the image's own health check asks) never ask for the password, because a console and the container's health check cannot send one. A link is only the file's path, encoded, so the password protects the app, not the files behind a link a console already holds, or one someone could work out from a file name. `/files/` is the older way to fetch a file by its path, and does ask.
- Basic authentication over plain HTTP is readable by anyone who can watch the network. That is a fair trade at home; put a TLS proxy in front of it if it is not.

## The log

The log is kept in memory for `/api/log` and written to `server.log` in the config folder, in two files of 4 MB. That matters because **a container keeps no memory across a restart**, which is exactly when you want to know what happened just before.

```bash
curl -s http://YOUR-SERVER:12867/api/log?since=boot | tail -50
```

Without `?since=boot` you get only what this process has logged, the last 400 lines. With it, you get the last 512 KB of the file, across one rotation (add `&bytes=` up to 4194304 for more). Without it the first line is the **startup line**, which names the build that is running (`build 2026-…` at its end); it is kept apart from the 400 lines, so it is there however much has been logged since. With it, every start of the app has written its own startup line into the file, so the build that is running now is the last of them, not the first line. If the config folder isn't writable the app runs exactly as before and the setup panel says the log is memory only.

**What a transfer logs.** A console fetches a package as a run of 16 MiB range requests, and one big send is hundreds of them. So a transfer gets a `download start` line when it begins, one `download complete` line (with how long it took and how fast) when every byte has gone out, and a `download ABORTED` line for every range the console hung up on before it finished — those are what the *Struggling* diagnosis in Troubleshooting is made of, so they are never left out. Set `LOG_RANGES=1` to also get a start and a done line for every single range.

`/healthz` and `/favicon.ico` are answered without a log line.

## Other files and Info

A library lists packages and archives, and after them every other file in the folder, under *Other files*, as an ordinary row with a type icon, its size and its date. **Other files** in the toolbar controls this. It is on unless a browser has turned it off, and that choice is remembered per browser. When it is off and a folder has other files, a quiet line under the list says how many and offers *Show them*. **Hidden** additionally shows names that start with a dot (folders, packages, archives and, with **Other files** on, other files); on its own it lists no other files. Up to 2,000 files are read from a folder and 300 are drawn at a time (*Show 300 more*). With `ALLOW_ANY_FILE` on, every non-empty file that is not an archive is listed as a package instead, so it is handled as a package (package Info, Send) and not as an other file.

**Every row has a checkbox**: packages, archives (`.rar` sets, `.zip`, `.7z`), other files and folders. Rows are selected with the checkbox, a click, **Shift**-click for a range, or the keyboard, and ticks stay when you move to another folder. The header box selects every file on screen (packages, archives and other files) and never folders; tick folders one at a time or with a **Shift** range. Clicking a folder's name or icon still opens it; only its checkbox ticks it. The bar at the bottom counts what is selected (*5 selected: 2 folders, 1 package, 1 archive, 1 other file*) and its buttons follow it:

- **Info** works for any selection (below).
- **Send** and **Copy link** work on the packages in the selection only; with none selected they are disabled, and with a mixture the confirmation says how many packages go and that the others are not sent.
- **Delete** acts on anything in the selection, including folders. It deletes files (packages, other files, `.zip` and `.7z`) through the usual dialog, which lists them and, when some are not packages, says so (*Not a package: ... They are ordinary files, deleted the same way*). With a folder in the selection, the dialog first works out what's inside it (*Working out what this deletes…*), then shows a summary before anything happens (*This permanently deletes 3 folders and 5 files — 428 files, 12.4 GB in all, including 6 games. This cannot be undone.*), lists the folders with their own counts or a reason if one is refused, and requires a checkbox, *I understand this cannot be undone*, before Delete works. A folder delete is checked and validated before anything is removed: nothing outside the selected folder is ever touched, even through a symlink or a junction inside it or in place of it, and a file being sent to a console or hashed anywhere inside a folder stops the whole delete with nothing removed. If something changes inside a folder while it's being deleted, mid-way, from another device or a download, that specific case is caught and the whole delete is reported as failed, but whatever was already removed up to that point stays removed; this is rare, and only happens if something else writes to the folder at that exact moment. A folder too large to check safely in one go is refused with that reason, and the library's root can't be deleted here. Up to 200 files go in one request; a bigger selection is sent in batches of 200 and the report says how many were refused and why.
- **Rename** takes one file, or several packages (the preview under [Renaming several at once](#renaming-several-at-once)). With other files in a larger selection it is disabled and says to select just the one, and one **folder** in a local library can be renamed on its own (a name only; refused while a console is downloading from it, a build, unpack, copy or move is using it, or a send is held for a package in it; what the app remembers about the folder follows the new name). Folders on a console, and a folder among other items, cannot. A package opens the rename dialog described under [Renaming a package](#renaming-a-package). For any other file it asks for a new name, and the extension may be changed after the question Explorer asks (*If you change a file name extension, the file may become unusable. Change it?*); an archive keeps its extension.
- **Open** is for one text file, chosen by its extension (below); a file with no extension is opened from its Info instead.

**Folders** can be ticked but not renamed or deleted from the page: a new name would break sends that are waiting and details ShadowPKG remembers, and a delete takes everything inside.

**New folder.** The folder-and-plus button at the far right of the path row (opposite the library picker) makes an empty folder in the folder on screen, in a local library or over FTP on a console. It is not there in a search, Needs attention, Homebrew or Recently added, where no folder is on screen. A name is judged the way a rename is: no slash, nothing that starts with a dot, none of `< > : " | ? *`, no trailing space or dot, no Windows device name (`CON`, `NUL`, `COM1`…), at most 255 bytes, and never one of the names ShadowPKG keeps for its own work folders. Nothing is ever replaced: a name that is taken, in any spelling of its capitals, is refused. None is made inside a build's or an unpack's scratch folder, through a link that leads out of the library, or in a library mounted read-only. A folder made in a local library is given permissions the PC and the console can write to (the same as the folders ShadowPKG makes for a build). `POST /api/mkdir` with `{src, dir, name}` does it for a script.

**RAR sets** are ticked like any other row. **Info** shows the set's details: its parts, the packages inside and the reason it is served, unpacked or left alone. **Delete** with exactly one set selected and nothing else opens the usual *Delete archive* dialog (see [Archives](#archives)), which lists every volume and refuses until the packages inside are unpacked; with a set mixed into a larger selection Delete is disabled (*Delete an archive set on its own*). **Rename** of a multi-part set shows the server's refusal. **Send**, **Copy link** and **Open** are disabled for a set, with the reason.

### Info

**Info** is the one button for details, and it follows the selection:

- One **package**, or a package inside an archive, opens the package's Info dialog (see [What a package says about itself](#what-a-package-says-about-itself)), which ends with a **File** section: the same rows (type, where it is, size, dates, attributes, what is using it) and the actions **Open folder**, **Copy path** and **Calculate SHA-256** (no SHA-256 for a package inside an archive, which has no file of its own).
- One **other file, archive or RAR set** opens the file details. For a file: its type (*PS4 package*, *ZIP archive*, *Text document*, ...), where it is (with a **Copy** button for the path as ShadowPKG knows it), its size in bytes as well as in GB, when it was Created, Modified and Accessed, and its attributes (*Read-only*, *Hidden*). An archive adds its parts and the packages inside. *In use* says when a console is downloading the file, a send is waiting for it, or it is being unpacked. The buttons are **Rename** (not for a package inside an archive), **Open folder**, **Copy path** and **Calculate SHA-256**, plus **Open** for a text file or a file with no extension and, when it can be edited, **Edit**. **Calculate SHA-256** reads the file once, with a progress bar, speed and **Cancel**, and gives the digest with a **Copy** button; closing the window cancels it; one runs at a time for the whole server, and it stops if a console starts downloading the same file.
- One **folder** opens the same details with how many files and folders it holds and their total size, counted while you watch (*Working out the size...*); a very large folder stops at 200,000 entries or 8 seconds and says *at least N files (stopped counting)*. Its **Open folder** goes into it. There is no Rename button for a folder, and a plain line says that a folder cannot be renamed or deleted here.
- **Several items** open a summary: how many of each kind (folders are counted separately and their contents are not added up), the total size of the files, the range of dates and the names. Its only action is **Delete**.

### Text files: viewing and editing

A file with a text-like extension (`txt`, `log`, `md`, `nfo`, `json`, `xml`, `ini`, `cfg`, `conf`, `csv`, `tsv`, `yml`, `yaml`, `toml`, `html`, `htm`, `css`, `js`, `mjs`, `sh`, `bat`, `cmd`, `ps1`, `py`, `rb`, `lua`, `c`, `h`, `cpp`, `hpp`, `cs`, `java`, `srt`, `sub`, `diz`, `readme`) opens in a viewer with **Open** in the bar, **Open** in its details, or a double-click on its row. The list is the same for viewing and editing, except that `readme` is view-only. A file with no extension has no bar or double-click shortcut; its Info has **Open**, and the server reads any ordinary file that passes the text check below. The viewer shows the name, then the size, encoding, line endings and how much is loaded, and the text in a scrolling monospace block. **Wrap lines** is remembered per browser, **Copy all** copies what is loaded, and **Load more** fetches the next 256 KiB (the server sends at most 1 MiB at a time, and reads only a few files at once, answering *busy, try again* beyond that). The text is shown as text, never as page markup, and only the piece asked for is read from disk, so a huge file costs no more than a small one. Viewing stops at 8 MiB; the viewer then says to copy the path and open the file on your PC. A file that does not look like text (a NUL byte or too many control characters in its first 64 KiB) is refused with *This does not look like a text file*; select it and press **Info** for its details instead.

The encoding is detected: a UTF-8, UTF-16LE or UTF-16BE byte order mark decides it, otherwise valid UTF-8 is UTF-8 and anything else is read as Windows-1252.

**Edit** turns the viewer into an editor. It is offered for a file of up to 2 MiB whose extension is in the list above (without `readme`), or a file with no extension of under 256 KiB, once the whole file has been loaded, and only when the file and its library are writable and no console is downloading it; otherwise it is disabled and its tooltip says why (*Too big to edit here*, *This kind of file cannot be edited here*, *This file is read-only, or its library is mounted read-only*, and so on). Packages, archives and executables are never edited. **Save** (or Ctrl/Cmd+S) writes the file, **Revert** drops your changes, and the title shows a dot while there are unsaved changes; Done, Escape, a click outside, opening another file or leaving the page all ask *Discard your changes?* first. A save keeps the file's encoding, byte order mark and line endings (a file with mixed endings asks *Save every line with which one?* on the first save, with **LF**, **CRLF** or **Cancel**), so opening a file and saving it unchanged gives the same bytes.

A save is safe against the usual accidents:

- **Atomic.** The new content is written to a temporary file in the same folder (its name starts `.shadowpkg-save-`), flushed to disk, then renamed over the original. If anything fails the original is left exactly as it was. A leftover temporary file from a crash is ignored and is hidden unless **Hidden** is ticked.
- **Conflict check.** If the file's size or modified time changed since you opened it, nothing is written and the page offers **Reload (lose my edits)**, **Save anyway** or **Cancel**.
- **Encodings.** A Windows-1252 file with characters it cannot hold is not saved with substitutes; the page lists them and offers **Save as UTF-8**.
- **Optional `.bak`.** While editing, **Keep a .bak copy** copies the file as it was when you opened it to `<name>.bak` beside it (replacing an older one). Only the first save makes it, so a later save does not overwrite it with an earlier save's text.
- **Refused**, each with a plain sentence: ShadowPKG's own files in the config folder, scratch and builder files and the files of a running build, a file that is being downloaded, hashed or unpacked, a package or archive, a link (edit the file it points to), a file with more than one name (a hard link, since a save would change only one of them), a read-only file, a library mounted read-only (a different message from a single read-only file), a file that no longer looks like text or has bytes that are not valid for its encoding, a text with a NUL character in it, a save whose encoding does not match the one the file is stored in, and a file that is or would become too big (2 MiB, or 256 KiB without an extension). Reading is refused only for ShadowPKG's own files in the config folder.
- **Limits.** At most 8 saves are worked on at once and a save body may be up to 4 MiB; beyond that the answer is *busy, try again* (HTTP 429).

### What the server refuses

For rename and delete: anything that belongs to a build or an unpack in progress (`.shadowpkg-build`, `.shadowpkg-extract-...`), the builder's own files at the top of a library, a text save's temporary file (`.shadowpkg-save-...`), ShadowPKG's own files and the `themes` folder in the config folder, the files of a dump while a build is running on it, a file that is being downloaded, hashed or unpacked, a path that leads out of the library through a link, and (for a new name) the names Windows reserves (`CON`, `NUL`, `COM1`...). The check is on the real file, so a different spelling, letter case, an 8.3 short name or a link to the same place does not get past it.

## Themes

The **Theme** button (the palette icon at the top) opens the Theme window: the fifteen built-in looks, then any you have added, with **Make a theme**, **Choose a file…**, **Choose a folder…** and the setting for what devices use by default. Below the themes is a separate **Background** section for a per-device page background image (cover, contain, fill or tile), independent of the theme.

- **Make one without typing code.** **Make a theme** asks for a name, a base look and four colours (background, panels, text, accent; good, bad and warning colours are optional). The page changes as you go, a readability report says whether every text-on-background pair is clear, and **Save for every device**, **Save on this browser**, **Download .json** and **Copy JSON** finish it.
- **Drop a file or a folder.** Drag a theme file (one `.json`) or a theme folder (`theme.json`, an optional `theme.css`, an `assets/` folder) anywhere on the page. A window shows the name, the colours and the readability report; **Try it** applies it with a bar to **Keep** or **Undo**, **Install for every device** saves it on the server, **This browser only** keeps it on this device. **Choose a file…** and **Choose a folder…** do the same where dragging is awkward, such as a phone.
- **Put it in the config folder by hand.** Files and folders in the `themes` folder inside the config folder are picked up within a couple of seconds, with no restart (the Theme window shows them when you open it). A file that is not valid is listed in the Theme window with the reason and is not used.
- **Readable by construction.** A theme gives four colours; the page works out every other colour it uses from them and moves any text colour that would be hard to read until it is clear. The same check runs on the built-in looks. A theme can still set any single colour itself, and the report says when that makes a pair hard to read.
- **Every device or one.** A device remembers its own choice. A device that has never chosen uses the server's choice: set it in the Theme window (*Every device without its own choice uses*) or with `DEFAULT_THEME`. **Use the server's choice on this device** forgets the device's own. A theme kept on one browser only has about 1 MB of room together, and a theme with an embedded font or picture takes about twice its file size there, so about 500 KB is the practical limit for those; install larger ones for every device.
- **What a theme is made of.** A theme is data, not code: colours, a background image or gradient, corner rounding, a font stack, and optional extra style rules. Everything is checked when it is added; a theme cannot run script or load anything from the internet, and its styling is limited to a list of allowed rules. That check refuses the common ways to hide or blank the page, but it cannot catch every one. If a theme ever makes the page unusable, open it with `?safe=1` at the end of the address: safe mode ignores custom themes for that visit, and you can then remove the theme. Pictures and fonts go inside a single file as `data:` addresses (the whole file up to 1 MiB, each embedded font up to 900 KB) or in a folder as ordinary files (up to 4 MiB, at most 24 files counting `theme.json` and `theme.css`). A folder theme can also replace the header logo and the row icons with its own pictures — a `logo` and an `icons` map in `theme.json` (see [docs/theme-extensions.md](docs/theme-extensions.md)).

The guides: [docs/THEMES.md](docs/THEMES.md) is for people (try the examples, make a theme, edit a file, every way to install, fix problems, with screenshots); [docs/THEMES-FOR-AGENTS.md](docs/THEMES-FOR-AGENTS.md) is the specification for an AI assistant asked to make a theme, with [docs/THEMES-REFERENCE.md](docs/THEMES-REFERENCE.md), [docs/theme.schema.json](docs/theme.schema.json) and [docs/theme-tokens.json](docs/theme-tokens.json). `node tools/themes/check.js <theme>` checks a theme with the real server and the real readability code; `node tools/themes/preview.js <theme> --out <folder>` takes screenshots of it (see the guides). Three examples are in `examples/themes/`.

## Keyboard

Folder, package, group and console rows can be reached with **Tab**; **Enter** or **Space** does what a click does (ticks a package or file, expands a group); on a folder, **Enter** opens it and **Space** ticks it. A button or checkbox inside a row keeps its own keys. **Shift**-click a row (or its box) to tick every row from the last one you clicked through it. `/` still jumps to the search box. The **↑ Up** button at the left of the library picker (and **Alt+↑**) goes up one folder at a time; it is not shown at the top of a library.

## Search

Searching covers the whole library, which means walking every folder and reading the index of every archive — minutes of work on a large collection. None of it happens while you wait: the list is built in the background and served from the last snapshot, and archives are read one at a time and remembered in `archives.json` in the config folder, so a restart costs nothing.

A query matches folder names as well as package paths, titles and IDs, and can carry operators alongside the free text — `kind:pkg|game|update|dlc|folder|ps4|ps5|homebrew`, `tag:dump|homebrew|unconfirmed`, `size:>50GB` (also `<`, `<=`, `=`; a bare size means "at least that"), `title:…` and `id:…` — and every one of them, plus the free text, has to hold.

A search run before that finishes returns what is known so far and says what is still outstanding, filling in as it goes — including how many packages have yet to be read for their titles, since searching by title is incomplete until that reaches zero. Browsing folders never waits on any of this — a folder is read when you open it.

A search that matches thousands of packages draws the first 300 rows and ends with a **Show 300 more** button, so a phone is not asked to build 20,000 rows at once (the Needs attention and Homebrew lists do the same). **Select all** still ticks every match, drawn or not, and its label says how many that is and that the ones not shown yet are included. Changing the search starts again at 300.

A search looks in the library you are in. With more than one library, **Search all N libraries instead**, under the results, widens it, and each result then names its library; a new search starts on the current library again. The list is rebuilt when a request finds it ten minutes old, and after a rename, delete or finished build. A folder you open is always read live, so a file you copy in shows there at once but reaches search, **Needs attention**, **Homebrew** and **Duplicates** later. **Refresh**, beside the search box, rebuilds the list now, rereads the library list and the open folder, and re-checks the consoles.

## Page weight

The page is sent gzipped to any browser that accepts it: about 190 KB instead of 1.6 MB (600 KB before compression once the picture below is cut out). Most of the difference is the logo's easter egg, a 750 KB picture kept inside `index.html` as text. The server cuts it out when it starts and serves it from `/egg.gif`, so it is only downloaded by someone who taps the logo ten times. `index.html` on disk still holds the picture, so it is still the same two files, and if the server cannot find the picture where it expects it, it serves the page as it is.

Answers over 16 KB are gzipped too, without holding up the transfers that are running. The one that matters is a library's package list, which grows with the number of packages and compresses well. `GET /api/list` also answers "not modified" while nothing in it has changed, so a search left open on a library that has settled does not fetch the whole thing again every few seconds. (While packages are still being read the list changes with each one, so the answer is a fresh list.) A client that does not send `Accept-Encoding: gzip` gets the plain bytes.

## How the link works

The console's installer hands the URL to the system downloader, which rejects spaces and `%`-escapes. So ShadowPKG builds links like:

```
/p/<base64url("<library id>\n<relative path>")>/<clean-name>.pkg
```

The real path travels in the token; the visible name is reduced to `A–Z a–z 0–9 . _ -`. Links are derived, never stored, so the same file always has the same URL and nothing is lost across restarts.

## Troubleshooting

**The console says "install failed" instantly.** Use the **Test** button next to that console. If it says the console refused the test without downloading anything, its installer is broken, not ShadowPKG — reload the payload or reboot it, check its Downloads queue for a stuck item, and check free storage. The app adds this note to a failed send automatically when it sees no request arrive. If Test says the console accepted the test but has not downloaded anything, the console may just be busy with another install.

**A transfer sits at a percentage with no explanation, or "no data for X" looks wrong.** Check whether the Activity bar says **Struggling to send** or **Stalled after failing** (the list says **Retrying**, or "N attempts failed before it went quiet") instead of a plain percentage — that means the console requested the same range over and over and the connection died partway through every time, not that nothing is happening. That's a network-path problem between the console and this server, not something ShadowPKG did: each `download ABORTED` line in the log is a range that went out at the right size and was hung up on partway (start the app with `LOG_RANGES=1` to see every request, start to finish). Most often it's the console on Wi-Fi rather than ethernet for a large file, something else on the network saturating the link, or a router that chokes once a transfer runs long enough. Try wired ethernet first if it's on Wi-Fi; a stalled transfer resumes on its own once the underlying path clears.

**`SCE_NP_DRM_CONTENT_ERROR_HEADERFORMAT`.** The console read the file's start and end and rejected the header. Usually the package is incomplete — a torrent that preallocates the full size looks complete-sized while pieces are still missing. Wait for the download to finish and send it again. ShadowPKG catches the plainest cases itself and says *Not sent* with the reason, without contacting the console: a file under 256 bytes, one whose header is not a package, one still being written (its size or time changes), or one whose last few KB are all zeros. A package missing pieces in the middle passes those checks, so only the console reports it.

**The Extract button is greyed out.** Hover it and the tooltip says why: the container has no extractor installed, the archive is password protected, or it is multi-part, split or incomplete (those have to be unpacked by hand). A library mounted read-only does not grey it: pressing the button then fails with "mounted read-only", because extraction writes the package next to its archive and that library needs read/write.

**The image was rebuilt but nothing changed.** A container keeps the image it was created with, so restarting it runs the old code with a fresh startup line. Recreate the container instead, and check the build timestamp. It is at the end of the startup line, which always leads `/api/log`, and `app.build` in `/api/diagnostics` has it too:

```bash
curl -s http://YOUR-SERVER:12867/api/log | head -1
```

**Disk space went missing next to an archive, and no folder shows where.** An unpack that was cut short — the container was stopped, recreated or killed for memory in the middle of it — leaves its half-unpacked files in a hidden `.shadowpkg-extract-<id>` folder. The setup panel lists them after the next start, with their size, and offers to remove them; see [Interrupted unpacks](#interrupted-unpacks). A stop or update while something is unpacking is the usual cause, so give an unpack of a big dump time to finish before updating the container.

**Nothing shows up in a folder.** Only `.pkg` files and archives (`.rar`, `.zip`, `.7z`) are listed. A "dump" release — a tree of game files with no package inside — is not something a console can install, so its files aren't listed; the folder itself is marked as a dump (see *Game dumps*). Tick **Hidden** in the toolbar to also see names starting with a dot and files that aren't packages, dimmed and tagged, for looking at only (they can't be sent), and archives in there can still be unpacked. It is remembered per browser. `ALLOW_ANY_FILE=1` is the server-wide version, which also lets those files be served.

An existing file of up to 2 MiB only (under 256 KiB without an extension); the body may be up to 4 MiB. Also refuses (403, 409 or 415) a package, archive, link, hard-linked or read-only file, ShadowPKG's own files, and a file that is busy or no longer looks like text; 429 when saves are queued. Written to a temporary file beside it and renamed over it. 409 when the file changed on disk since it was read (unless `overwrite`), 400 with the characters listed when they do not fit the encoding, 413 when too big. Answers `{ok, size, mtime, encoding, lineEnding}`, and `backup` when a `.bak` was kept. |
| `GET /api/properties?src=&path=` | Everything the Info dialog shows for a file, a folder (`contains: {files, dirs, bytes, truncated}`, counted by a bounded walk: at most 2 at a time, 429 when more are waiting) or a package inside an archive (`archive.rar!/inner.pkg`): type, size, dates, attributes, package details, archive parts, what is using it. |
| `POST /api/hash`, `GET /api/hash`, `POST /api/hash/cancel` | SHA-256 of one file: `{src, path}` starts it and answers `{id}`; `GET /api/hash?id=` gives `{state, bytes, total, speed, sha256}`; with no id it says which job is running; cancel takes `{id}` or nothing. One at a time (409 says what is running); a job nobody polls is stopped after two minutes; refused while a console is downloading the file. |
| `GET /api/themes` | The installed themes as summaries (`id, name, author, description, version, base, mode, palette, form, bytes, hasCss, hasTokens, hasFonts, editable`), `rejected` (files not used, with the reason), `default` and `defaultFrom` (the server's choice), `writable` and `max`. ETag. |
| `GET /api/themes/:id` | One theme in full: the summary plus `tokens`, `css`, `fonts` and `source`, the cleaned manifest (posting it back to `/api/themes/check` gives the same theme). ETag; 404 for an id that is not installed. |
| `POST /api/themes/check` | Check a theme and write nothing: `{theme: {…}}` for a single file or `{files: {"theme.json": "…", "assets/x.png": "<base64>"}}` for a folder (up to 6 MiB). Answers `{ok: true, theme, warnings}` or 400 `{ok: false, problems}`. |
| `POST /api/themes`, `DELETE /api/themes/:id` | Install a theme (same body as `check`, plus `replace: true` to overwrite an id that exists; 409 `exists` otherwise; 403 when the config folder is read-only; 409 past 64 themes) or remove one. |
| `GET /themes/:id/assets/:file` | A folder theme's picture or font, served with `nosniff`, and for SVG a sandboxing content-security-policy. |
| `GET /api/config` | Everything the Settings window shows: each setting that can change while running (its value now, where it came from, what the variable says, a note when it is set to something that does not work) and the fixed ones. A secret such as `NOTIFY_URL` is returned as its host only. |
| `POST /api/settings` | Change settings: `{app: {EXTRACT_PARALLEL: 3, SCRATCH_LIBRARY: "fast", NOTIFY_URL: ""}}`, a key set to `null` handing it back to its variable; the whole request is checked first and a bad value changes nothing. Returns what `GET /api/config` does. Set `PUBLIC_BASE` at runtime: `{publicBase: "http://192.168.1.10:12867"}`, or blank to clear it; `{defaultTheme: "sunset"}` sets the theme devices use until they choose (blank clears; the id must be built-in or installed). Kept in `settings.json` in the config folder; takes priority over the environment variable and needs no container recreate. Anything that is not `http(s)://host[:port]` is a 400, and a config folder that is not writable is a 409. |
| `GET /api/log` | The last 400 lines of the server log. Its first line is the startup line, which names the running build. Add `?since=boot` for the tail of the file on disk, which reaches back past restarts (and so holds one startup line per start; the last is the running build). |
